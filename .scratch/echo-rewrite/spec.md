# Echo

Status: ready-for-agent
สร้าง: 2026-09-12

---

## Problem Statement

ผู้เล่นอยากได้เครื่องมือช่วยยิงใน CS2 ที่ให้ความรู้สึกเหมือน **"วันที่มือขึ้น"** ไม่ใช่
**"มือของคนอื่น"** — **ช่วยปิดมุมเข้าหาเป้า** โดยไม่แย่งการควบคุมไปจากผู้เล่น

*(เดิมเขียนว่า "ช่วยติดตามเป้าที่สไตรฟ์ใต้แรงสะท้อน" ซึ่งขัดกับ User Story ทุกข้อ —
ไม่มี story ไหนขอการติดตามเลย ดูหัวข้อถัดไป)*

### ทำไมถึงเป็นการปิดมุม ไม่ใช่การติดตาม — เหตุผลจาก CS2

- **นัดแรกคือนัดที่ฆ่า** ยืนนิ่งยิงไรเฟิลนัดแรกแม่นเป๊ะ หัวนัดเดียวจบ จังหวะชี้ขาดคือ
  เสี้ยววินาทีก่อนนัดแรก ไม่ใช่ช่วงยิงยาว
- **สเปรย์เป็นแพตเทิร์นตายตัวที่คนเล่นจำด้วยกล้ามเนื้อ** อะไรที่เข้าไปยุ่งกลางสเปรย์
  คือไปสู้กับสิ่งที่ผู้เล่นฝึกมา — และคือ K1 เป๊ะ
- **ขยับแล้วกระสุนกระจาย** ดวลจึงสั้น 200–400 ms **ไม่มีหน้าต่างยาวให้ติดตาม**

ต่างจากเกมที่ยิงรัวยาว ซึ่งการติดตามคือทุกอย่าง

**กติกา: กดหนึ่งครั้ง ดึงหนึ่งครั้ง** พอวิวเข้าเขตตัวเป้าแล้ว จบ — ที่เหลือเป็นของผู้เล่น
จนกว่าจะปล่อยปุ่มแล้วกดใหม่

**ส่งมอบที่ความกว้างลำตัว ไม่ใช่ความกว้างหัว** — ดึงจบที่หัวคือมันเล็งให้ ดึงจบที่ลำตัว
คือมันปิดมุมให้แล้วเหลือการเล็งไว้ นี่คือเส้นแบ่งที่ชื่อโปรดักต์ตั้งอยู่บนมัน

และมันไม่ต้องมีกฎเรื่องระยะเลย — ลำตัวกินมุมน้อยลงเมื่อไกลขึ้น **ยิ่งไกล ยิ่งยิงยาก
ยิ่งเห็นชัดว่ามีตัวช่วย ก็ยิ่งแตะน้อยลงเอง**

| ระยะ | มุมลำตัว | มุมหัว |
|---|---|---|
| 500 | 1.83° | 0.57° |
| 1000 | 0.92° | 0.29° |
| 2000 | 0.46° | 0.15° |

มีโปรดักต์เดิมที่ทำสิ่งนี้ได้ดีอยู่แล้ว แต่**ต่อยอดไม่ได้** — เจ้าของไม่สามารถเข้าใจหรือ
เปลี่ยนมันได้ในความเร็วที่ต้องการอีกต่อไป

**สิ่งที่ต้องการคือโปรดักต์ที่เจ้าของเข้าใจทุกบรรทัด และเติบโตต่อได้**

---

## Solution

**Echo คือโปรดักต์ใหม่ ไม่ใช่การเขียนของเดิมใหม่**

สร้างขึ้นทีละขั้น แต่ละขั้นเล็กพอที่จะเข้าใจได้ทั้งหมด และ**เห็นผลได้ด้วยตา**ก่อนขึ้นขั้นถัดไป

ของเดิมกลายเป็น **คลังความรู้** ที่หยิบมาใช้เมื่อถึงขั้นที่ต้องการ — ไม่ใช่แม่แบบที่ต้อง
ถ่ายทอดให้ครบ

### สิ่งที่ **ไม่ใช่** เป้าหมาย

| ไม่ใช่เป้าหมาย | เหตุผล |
|---|---|
| **พฤติกรรมเหมือนของเดิมทุกอย่าง** | Echo เป็นโปรดักต์ใหม่ ความต่างไม่ใช่ข้อบกพร่อง |
| เทียบตัวเลขวัดผลกับของเดิมได้ | ออกแบบการวัดใหม่ได้อิสระ |
| ยกโค้ดเดิมมา | ยกเฉพาะ**ข้อเท็จจริง** ไม่ยก implementation |
| ทำให้ครบทุกฟีเจอร์เร็วๆ | ขั้นละอย่าง เข้าใจก่อนไปต่อ |

## หลักการ

สี่ข้อนี้คุมทุกการตัดสินใจ **การขัดหลักการต้องเป็นการตัดสินใจที่ประกาศชัด ไม่ใช่ผลข้างเคียง**

| | หลักการ | ในทางปฏิบัติ |
|---|---|---|
| **P1** | **มือผู้เล่นชนะเสมอ** | ทุกอย่างที่ระบบทำ ผู้เล่นแย่งคืนได้โดยไม่ต้องปล่อยปุ่ม และไม่ต้องรออะไรนอกจากการดันของตัวเอง — ดูข้อแก้ไขด้านล่าง |
| **P2** | **สงสัยเมื่อไหร่ ไม่ทำ** | หลักฐานที่เก่า ขาด หรือไม่แน่ใจ = ไม่ทำงาน ห้ามเดา |
| **P3** | **เกมต้องไม่รู้สึกถึงเรา** | ไม่เสีย FPS ไม่กระตุก ไม่กิน CPU ตอนอยู่เฉย |
| **P4** | **เข้าใจทุกบรรทัดที่เขียน** | ถ้าอธิบายไม่ได้ว่าทำไมบรรทัดนี้อยู่ตรงนี้ อย่าเขียน |

**P4 คือข้อที่ทำให้โปรเจกต์นี้ต่างจากของเดิม** และเป็นเหตุผลที่ต้องไปทีละขั้น

### ข้อแก้ไข P1 — จาก "ทันที" เป็น "ภายในเวลาที่กำหนด"

เดิม P1 เขียนว่า **แย่งคืนได้ทันที** และตอนทำขั้น "มือชนะ" ก็ทำแบบนั้นจริง —
มือขยับเฟรมไหน หยุดช่วยเฟรมนั้น

**ผลคือใช้ไม่ได้** บัญชีของรอบจริงอ่านว่า `hand=2853 steering=359` — มือชนะสามในสี่ของ
เวลา ไม่ใช่เพราะผู้เล่นคุมวิวสามในสี่ของเวลา แต่เพราะตัวช่วย**กระพริบติดดับวินาทีละหลายครั้ง**
เจ้าของอธิบายว่า *"มันแข็งไป"* ซึ่งตรงกับตัวเลขพอดี

**ข้อแก้ไข:** ความแรงไต่ขึ้นลงตามเวลาแทนการติด/ดับ ผู้เล่นยังได้วิวคืนครบโดยไม่ต้องปล่อยปุ่ม
แต่ใช้เวลาเท่ากับช่วงไต่ลง **ไม่ใช่เฟรมเดียว**

| | ก่อน | หลัง |
|---|---|---|
| มือชนะ | 77% ของ pass ที่กดค้าง | **10.7%** |
| ความรู้สึก | กระพริบ | เกาะได้ทั้งยก 29 วินาที มือฝืน 17% |

**สิ่งที่แลกไป:** "ทันที" หายไปจริง และนี่**เป็นการเปลี่ยนหลักการ ไม่ใช่การปรับตัวเลข**
บันทึกไว้เพื่อว่าถ้าวันหนึ่งรู้สึกว่ามันไม่ยอมปล่อย จะได้รู้ว่าต้องมาดูตรงไหน และรู้ว่ามันเป็น
การตัดสินใจ ไม่ใช่ความบังเอิญ

### ตัวเลขที่ขั้น 6–8 ตัดสินไปแล้ว

| ของ | ค่า | ที่มา |
|---|---|---|
| องศาต่อ mouse count | −0.0196 | วัด 5 ครั้ง ลงที่เดิมทุกครั้ง — **ของ sens ผู้เล่น ไม่ใช่ของเกม** |
| ตาเรา สูงจากเท้า | 64 | E3 — **ข้อเท็จจริงของเกม** จุดที่วัด*จาก* |
| เล็งบนตัวเขา สูงจากเท้า | 55 (อก) | **การตัดสินใจของเรา** จุดที่วัด*ไป* — ดู E8 |
| ส่วนของระยะที่ปิดต่อ pass | 0.35 | เข้าเป้า ~70 ms |
| เพดานต่อ pass | 250 counts โค้งเข้าหา | ไม่มีมุมให้รู้สึก |
| ดันเต็มแรง | 750 counts/วินาที ≈ 15°/วินาที | เป็น**ความเร็ว** ไม่ใช่จำนวน counts ต่อ pass — ไม่งั้นเครื่องที่รันคนละความเร็วจะได้โปรดักต์คนละตัว |
| ไต่ขึ้น / ไต่ลง | 40 / 120 ms | กดไกปืนยาว 50–100 ms — ไต่ 140 ms ทำให้ grip ขึ้นแค่ 20–44% ก่อนปุ่มขึ้น ปิดมุมได้ ~1° จาก 5° |
| จุดสมดุล | ≈11°/วินาที | **ไม่ใช่ค่าคงที่** — ออกมาจาก `fall / (rise + fall)` ต่ำกว่านี้ grip ไต่ขึ้นถึงมือจะขยับอยู่ |
| ยอมให้จอดห่างจุดเล็ง | 6 หน่วย ตามระยะจริง | **นี่คือจุดจอด ไม่ใช่ขีดจำกัด** ดู E9 — ดึงจบที่หัวคือมันเล็งให้ ดึงจบที่อกคือมันปิดมุมให้ |

## User Stories

### ปลายทาง — สิ่งที่ Echo จะทำได้ในที่สุด

1. ในฐานะผู้เล่น ฉันอยากเห็นศัตรูบนจอ เพื่อที่ฉันจะอ่านสถานการณ์ได้
2. ในฐานะผู้เล่น ฉันอยากได้ตัวช่วยปิดมุมเข้าหาเป้าขณะกดปุ่มค้าง เพื่อที่ฉันจะชนะดวลที่ควรชนะ
3. ในฐานะผู้เล่น ฉันอยากให้ตัวช่วยยอมแพ้ให้มือฉันเมื่อฉันฝืน โดยไม่ต้องปล่อยปุ่ม เพื่อที่ฉันจะไม่ต้องสู้กับมัน
   *(เดิมเขียนว่า "ทันที" — ดูข้อแก้ไข P1 ทำแล้วใช้ไม่ได้)*
4. ในฐานะผู้เล่น ฉันอยากได้ตัวช่วยหักล้างแรงสะท้อน เพื่อที่สเปรย์จะอยู่ในเป้า
5. ในฐานะผู้เล่น ฉันอยากให้ไม่มีอะไรทำงานตอนที่ฉันไม่ได้กดปุ่ม
6. ในฐานะผู้เล่น ฉันอยากให้ไม่มีอะไรทำงานตอนเกมไม่ได้อยู่หน้าสุด หรือฉันอยู่ในเมนู
7. ในฐานะผู้เล่น ฉันอยากปรับความแรงของทุกอย่างได้เอง

### ระหว่างทาง — สิ่งที่เจ้าของต้องได้จากการสร้าง

8. ในฐานะเจ้าของ ฉันอยากเห็นผลของแต่ละขั้นด้วยตา เพื่อที่ฉันจะรู้ว่ามันทำงานจริง
9. ในฐานะเจ้าของ ฉันอยากให้แต่ละขั้นเล็กพอที่ฉันจะเข้าใจได้ทั้งหมด
10. ในฐานะเจ้าของ ฉันอยากให้ขั้นที่ไม่ส่ง output มาก่อน เพื่อที่ความผิดพลาดช่วงแรกจะไม่มีผลอะไร
11. ในฐานะเจ้าของ ฉันอยากหยิบความรู้จากของเดิมมาใช้เมื่อถึงขั้นที่ต้องการ ไม่ใช่ยกมาก่อนทั้งหมด
12. ในฐานะเจ้าของ ฉันอยากให้ตรรกะที่ตัดสินใจอะไรสักอย่าง ทดสอบได้โดยไม่ต้องเปิดเกม

## Implementation Decisions

### บันได

```
 1  ต่อโปรเซส CS2 อ่านค่าได้หนึ่งค่า
 2  หาศัตรูเจอ พิมพ์ตำแหน่งออกมา
 3  วาดอะไรก็ได้ทับจอเกม
 4  วาดกล่องบนศัตรู                    ← ฟีเจอร์แรกที่ใช้งานได้
────────────────────────────────────  ยังไม่แตะเมาส์เลย
 5  อ่านเมาส์จริงของผู้เล่น
 6  ส่งการขยับเมาส์ออกไปได้
 7  ขยับเข้าหาเป้า                      ← ตัวช่วยเล็งตัวแรก แบบดิบ
────────────────────────────────────  จากนี้เติมความปลอดภัยทีละชั้น
 8+ มือชนะ · recoil · การพิสูจน์ · ...
```

**กฎของบันได**

- **ขั้นละอย่าง** ไม่ข้าม ไม่ทำสองขั้นพร้อมกัน
- **ทุกขั้นต้องเห็นผลด้วยตา** ไม่ใช่แค่ผ่าน test
- **ขั้นที่ไม่ส่ง output มาก่อน** (1–4) ทำผิดก็แค่วาดผิด
- **ออกแบบตอนถึงขั้นนั้น** ไม่ออกแบบล่วงหน้า
- **ขึ้นขั้นถัดไปได้เมื่อขั้นปัจจุบันอธิบายได้ทั้งหมด**

### สิ่งที่หยิบจากของเดิม — **ข้อเท็จจริง ไม่ใช่โค้ด**

หยิบเมื่อขั้นนั้นต้องการ ไม่ยกมาก่อน

| ข้อเท็จจริง | ใช้ที่ขั้น | ทำไมไม่เขียนใหม่ |
|---|---|---|
| ตาราง offset ของ CS2 | 1, 2 | เป็นผลของการไล่แกะ ไม่ใช่ตรรกะ — เขียนใหม่ = ไล่หาใหม่หลายสัปดาห์ |
| การแปลงองศา → จำนวนนับเมาส์ | 6, 7 | สอบเทียบกับเมาส์จริงแล้ว |
| เรขาคณิตของ hitbox | 4, 7 | แกะจาก asset ของเกม |
| **บัญชีเงื่อนไขปฏิเสธ 61 ข้อ** | **8+** | บั๊ก 61 ตัวที่เคยเจอในรอบจริง — **นี่คือคลังที่มีค่าที่สุด** |
| บทเรียนจากความล้มเหลว | 7, 8+ | ดูหัวข้อถัดไป |

**ทุกอย่างที่เหลือเขียนใหม่** — ตรรกะ · โครงสร้าง · test · การวาด · การส่ง input

### การอ่านเมาส์ของผู้เล่น — ต่อสายแล้ว

อ่านก่อนใช้สองขั้น ตามกฎของบันไดที่ว่าขั้นที่ไม่ส่ง output มาก่อน การอ่านเมาส์ผิดไม่มีผลอะไร
ส่วนการส่งเมาส์ผิดทำให้เมาส์กระตุกจริง แยกกันไว้แปลว่า**ถ้าขั้นส่งพัง จะรู้แน่ว่าไม่ใช่เพราะฝั่งอ่าน**

ตอนนี้ต่อสายแล้วที่ขั้น "มือชนะ" และมันคือ**ทางเดียวที่ระบบรู้ว่าต้องปล่อย**
อะไรที่เปลี่ยนสิ่งที่ไหลผ่านมันได้ ก็เปลี่ยนจังหวะที่ผู้เล่นได้วิวคืน

**ถ้าอ่านเมาส์ไม่ได้เลย ระบบต้องไม่ทำงาน** ไม่ใช่ถือว่ามือนิ่ง — มืออยู่เฉยกับมืออ่านไม่ได้
ต่างกันตรงที่อย่างหลังแปลว่า**ไม่มีทางแย่งคืนได้เลย** และถ้าเดาผิดทางนี้ ระบบจะเกาะแน่นที่สุด
ในจังหวะที่ผู้เล่นทำอะไรไม่ได้เลย

### สิ่งที่ตัดสินตอนถึงขั้นนั้น ไม่ตัดสินตอนนี้

โครงสร้างโมดูล · รูปแบบการจัดการสถานะ · การแบ่ง phase · รูปแบบการปฏิเสธ · การวัดผล

**ตอนนี้ยังไม่มีข้อมูลพอที่จะตัดสินเรื่องพวกนี้ และการตัดสินไปก่อนคือการเดา**

## Testing Decisions

### อะไรคือ test ที่ดี

- **ทดสอบพฤติกรรมภายนอก ไม่ใช่วิธีที่มันทำ**
- **ตรรกะที่ตัดสินใจอะไรสักอย่าง ต้องทดสอบได้โดยไม่เปิดเกม** — ถ้าทดสอบไม่ได้ แปลว่า
  มันพันกับการอ่านเกมมากเกินไป แก้ที่โครงสร้าง ไม่ใช่แก้ที่ test
- **เวลาเป็นค่าที่ส่งเข้าไป ไม่ใช่การรอ** — test ที่ `sleep` คือ test ที่ทดสอบ scheduler
- **test ใหม่ต้องแดงด้วยเหตุผลที่มันอ้าง** — ก่อนรับเข้า ให้ลบเงื่อนไขที่มันอ้างว่าตรึงไว้
  แล้วรันทั้งชุด ต้องแดงเฉพาะตัวนั้น

### ห้ามทำ

- **test ที่อ่านข้อความ source ของไฟล์อื่น** — ของเดิมทำแล้วพัง จนต้องมีกฎห้ามจัดรูปแบบโค้ด
- **test ที่ต้องเปิดเกมถึงจะรันได้**
- **mock ของโปรเซสเกม** — การอ่านเกมพิสูจน์ด้วยการเห็นมันทำงาน ไม่ใช่ด้วย test

### ขั้น 1–4 แทบไม่มี test

มันคือการต่อท่อและการวาด **พิสูจน์ด้วยตา** test เริ่มมีความหมายจริงตอนมีตรรกะที่ตัดสินใจ
— ขั้น 7 เป็นต้นไป

## Further Notes

### บทเรียนจากของเดิม — หยิบมาใช้ตอนถึงขั้น 7+

ทั้งสามข้อเป็น *อาการ → การวัด → สาเหตุ → การแก้* ที่เกิดขึ้นจริงและแก้ไปแล้ว
**อ่านก่อนถึงขั้นนั้น จะประหยัดเวลาไปมาก**

**K1 — ลำดับการคำนวณ recoil กับการนำเป้า สลับกันไม่ได้**
เคยทำ recoil ทีหลัง ผลคือชดเชยสองเท่า + อาการสั่นเป็นจังหวะตามการยิง → ภาพสั่น
ต้องวางแผน recoil ก่อน แล้วให้ตัวนำเป้ามองทิศ**หลัง**การชดเชย

**K2 — ห้ามตีความการขยับมือ ณ จังหวะที่กดปุ่ม ว่าเป็นการแย่งคืน**
เคยทำ แล้วการกดขณะมือกำลังขยับ — *ซึ่งคือสิ่งที่ผู้เล่นทุกคนทำ* — ทำให้ระบบข้ามการทำงาน
ทั้งรอบ **วัดได้ว่าเกิด 6 ครั้งทุก 30 วินาทีของการเล่น** และคือที่มาของอาการ
*"กดแล้วไม่มีอะไรจับ"*

**K3 — การหมุนตัวเลือกลงเพื่อลดอาการ อาจทำให้อาการแย่ลง**
ถ้าฝั่งสะสมกับฝั่งใช้ถูกคูณด้วยตัวคูณไม่เท่ากัน ที่ค่า 0 จะไม่มีอะไรมาล้างค่าที่สะสมไว้เลย

### บทเรียนที่ Echo เห็นเอง

ต่างจากหัวข้อบน — ไม่ได้รับมรดกมาจากของเดิม แต่เห็นจาก log ของตัวเองระหว่างสร้าง

**E1 — pointer ของ pawn เปลี่ยนทุกครั้งที่เกิดใหม่ ห้าม cache**

log ของขั้น 3 บันทึกวงจร ตาย → ดูคนอื่นเล่น → เกิดใหม่ ไว้ครบ และ address เปลี่ยนสามครั้ง
ในสามสิบวินาที

```
health=100  pawn=A     อยู่ในรอบ
pawn=none              ตาย
health=0    pawn=A     ศพยังถูกอ้างถึงชั่วครู่
health=0    pawn=B     ← address เปลี่ยน
health=100  pawn=C     ← เปลี่ยนอีก เกิดใหม่
```

**ต้องอ่าน pointer ใหม่ทุก tick** ถ้าเก็บไว้ใช้ซ้ำจะได้ข้อมูลจากหน่วยความจำที่เกมปล่อยไปแล้ว
และอาจถูกจองใหม่เป็นอย่างอื่น — **อ่านได้ ไม่ error แต่เป็นขยะ** ซึ่งเป็นความล้มเหลวที่แย่ที่สุด
เพราะมันเงียบ

นี่คือเหตุผลที่ของเดิมมีกลไกเรื่องอัตลักษณ์และรุ่นทั้งชุด — เราเห็นสาเหตุด้วยตาเองแล้ว
ไม่ใช่รับมาเป็นกฎลอยๆ

**ผลต่อขั้นถัดไป:** ขั้น 4 ต้องเดินรายการ entity ซึ่งเต็มไปด้วย pointer แบบเดียวกันนี้
เป็นสิบๆ ตัว ปัญหาเดียวกันจะใหญ่ขึ้นสิบเท่า

**E2 — "ไม่มีอยู่" เป็นสถานะปกติ ไม่ใช่ความล้มเหลว**

pawn เป็น null ตลอดเวลาที่อยู่ในเมนู ระหว่างรอบ และตอนดูคนอื่นเล่น ซึ่งเป็นเวลาส่วนใหญ่
ของการเปิดเกมทิ้งไว้ โค้ดที่ถือว่านั่นคือ error จะส่งเสียงตลอดเวลาโดยไม่มีอะไรผิด

และการอ่านทะลุ pointer อาจล้มเหลวได้เพราะ pawn ถูกปล่อยระหว่างการอ่านสองครั้งในจังหวะเดียว
— **ถือเป็น "ตอนนี้ไม่มีผู้เล่น" แล้วลองใหม่ tick หน้า ไม่ใช่ความผิดพลาด**

**E3 — ตำแหน่งของ entity คือเท้า ไม่ใช่ตา**

`cl_showpos` ของเกมรายงาน**ตำแหน่งตา** ส่วนฟิลด์ origin ของ entity เก็บ**ตำแหน่งเท้า**
ต่างกันเท่ากับ view offset ซึ่งคือ **64 หน่วยตอนยืน** และเก็บเป็นฟิลด์แยก

ตอนขั้น 4 การเทียบสองค่านี้ทำให้เสียเวลาไปหนึ่งรอบ — สร้างตัวตรวจ ดัมป์หน่วยความจำ
ตั้งสมมติฐานว่าอ่านผิดฟิลด์ ทั้งที่**ค่าถูกมาตลอด แค่เป็นคนละปริมาณ**

**สิ่งที่ต้องจำ:** อะไรก็ตามที่เล็งไปที่ผู้เล่นต้องใช้ตาหรือ hitbox ไม่ใช่ origin

**บทเรียนที่กว้างกว่านั้น:** ก่อนสรุปว่าอ่านผิด **ตรวจก่อนว่ากำลังเทียบของอย่างเดียวกันหรือเปล่า**
สัญญาณที่ควรจับได้เร็วกว่านี้คือ **ค่าต่างกันเป็นจำนวนเต็มคงที่เป๊ะ** — ความผิดพลาดของการ
อ่านหน่วยความจำให้ค่าขยะ ไม่ให้ค่าที่คลาดเคลื่อนพอดี 64.00

**E4 — หมุนขวาแล้ว yaw ลด และการวัดมุมจากสองค่าอ่านได้ไม่เกินครึ่งรอบ**

ขั้น 6 ส่งการขยับไปทางขวา แล้ว yaw **ลดลง** — เอนจินนับ yaw ทวนเข็ม นี่เป็นข้อเท็จจริง
ที่วัดได้จาก log ของเราเอง ไม่ใช่ข้อสันนิษฐาน และขั้นที่ต้องเล็งจะพึ่งมันโดยตรง

**ตัวเลขที่วัดได้: −0.0196 deg/count** จากการกดค้าง 5 ครั้ง ครั้งละ ~1000 counts
ทุกครั้งลงที่ −0.0195 ถึง −0.0197 (เทียบ `m_yaw 0.022` ได้ sens ≈ 0.89 ของเครื่องที่วัด)

**ตัวเลขนี้ขึ้นกับ sensitivity ของผู้เล่น ไม่ใช่ค่าคงที่ของเกม** ขั้นที่ต้องเล็งต้องหาค่านี้เอง
— อ่านจากเกม หรือวัดเอาตอนเริ่ม — ไม่ใช่ฝังตัวเลขนี้ลงไป

กว่าจะได้ตัวเลขนี้ พลาดสองชั้น ทั้งสองชั้นคือ**เครื่องวัด ไม่ใช่ของที่วัด**

1. **วัดจากมุมสองค่า** — ส่ง 3976 counts รายงาน 11 องศา ทั้งที่ควรได้ 126 เพราะวัด
   "ทางใกล้" ซึ่ง**แยกการหมุน 11 องศากับ 371 องศาออกจากกันไม่ได้** มุมสองค่าเดียวกันเป๊ะ
   → การหมุนที่ยาวกว่าครึ่งรอบต้อง**บวกทีละก้าว** ก้าวหนึ่งเฟรมเล็กเกินกว่าจะถูกเข้าใจผิด
2. **วัดครั้งเดียวตอนจบ** — ครั้งแรกได้ −0.0317 ซึ่ง**เพี้ยนเพราะมือผู้เล่นขยับไปด้วย**
   (log เฟรมนั้นมี 9–11 packets) ถ้าไม่บันทึกระหว่างทางก็ไม่มีทางรู้ว่าอัตรานิ่งหรือไม่

**สิ่งที่ต้องจำ:** ตัวเลขที่ได้จากการรวมยอดตลอดช่วงยาวๆ ไม่มีทางบอกได้ว่ามันนิ่งหรือเปล่า
**บันทึกระหว่างทาง แล้วดูว่ามันลงที่เดิมทุกครั้งไหม**

**E5 — หางของ stage ไม่ใช่ราคาของ stage นั้นเสมอไป**

log ขั้น 6 มีเฟรมที่อ่านเมาส์แล้วกิน 0.788 ms ทั้งที่**ไม่มี packet เข้ามาเลยสักตัว** และ
รอบก่อนหน้า stage ที่ขยับหน้าต่างก็กิน 0.789 ms ขนาดเท่ากันเป๊ะ — **มันคือจังหวะที่ OS
พาเธรดออกไป แล้วเวลานั้นตกใส่ stage ที่บังเอิญกำลังทำงานอยู่**

ก่อนจะมีตัวนับ packet ตัวเลขชุดเดียวกันดูเหมือนราคาต่อ packet เป๊ะๆ (11 packets → 2.4 ms,
9 → 0.85, 0 → 0.003) และข้อสรุปที่ได้คือ "ต้องอ่านทีละหลาย packet" ซึ่ง**ผิด**

**สิ่งที่ต้องจำ:** ตัวเลข worst frame คือหาง ไม่ใช่ค่าเฉลี่ย ก่อนจะแก้อะไรตามมัน
**ต้องมีหน่วยที่สองที่บอกปริมาณงาน** ไม่ใช่แค่เวลา — เวลาอย่างเดียวแยก "งานเยอะ" กับ
"โดนแย่ง CPU" ไม่ออก และสองอย่างนี้แก้คนละทางกันสิ้นเชิง

**E6 — สิ่งที่เราฉีดเข้าไป ไม่ย้อนกลับมาที่ raw input ของเราเอง**

ยิงการขยับเข้าไป 982 ครั้งใน 8.2 วินาที โดยผู้เล่นไม่แตะเมาส์ → **ได้ 0 packets**
สิ่งที่เข้ามาทาง raw input คือมือผู้เล่นล้วนๆ

ถ้าเป็นจริงเสมอ ขั้น "มือชนะ" ไม่ต้องหักของตัวเองออกก่อน — แต่**วัดมาจากเงื่อนไขเดียว**
(หน้าต่างเราอยู่เบื้องหลัง เครื่องนี้) ขั้นที่ต้องพึ่งมันต้องวัดซ้ำเอง ไม่ใช่รับมาใช้เลย

**E7 — บัญชีเงื่อนไขจับของได้ตั้งแต่บรรทัดแรกที่เขียน**

กฎข้างล่างบอกให้ทุกเงื่อนไขมีตัวนับ พอลงมือทำจริง **บัญชีที่เขียนขาดไปหนึ่งตัวจาก
สิบตัว** — ความเงียบแบบเดิมเป๊ะ โผล่มาในเครื่องมือที่สร้างมาแก้ความเงียบ

จับได้เพราะ `match` ที่ต้องครบทุกกรณี และมี test ที่ตรึงบัญชีไว้กับรายการจริง

และมันใช้งานได้จริงในรอบถัดมา: `no-enemy` ค้างที่ 0 ตลอดสองรอบแรก จนรอบที่สาม
ขึ้นเป็น 79 — **ก่อนหน้านั้นแยกไม่ออกเลยว่า "ไม่เคยเกิด" หรือ "ตายไปแล้ว"**

**สิ่งที่ต้องจำ:** บัญชีต้องพิมพ์ทุกตัวรวมทั้งศูนย์ บรรทัดที่พิมพ์แต่ของที่เกิดขึ้น
คือความเงียบเดิมในรูปแบบที่สั้นลง

**E8 — จุดที่เล็ง กับขนาดที่ยอมรับ ต้องพูดถึงรูปเดียวกัน**

ออกแบบไว้ว่า **เล็งที่หัว ส่งมอบที่ความกว้างลำตัว** ฟังดูสมเหตุผล — ปิดมุมใหญ่ให้
เหลือเศษสุดท้ายเป็นของผู้เล่น

**ผลคือยิงไม่โดน** log จับได้ตรงๆ: กดไก 15 ครั้งใน 3 วินาที ทุกครั้งตอบ "ส่งมอบแล้ว"
โดยไม่ขยับอะไรเลย และทุกครั้งห่างเป้า 1.15°

```
[22.428] delivered   off 1.15 deg   1 passes
[22.622] delivered   off 1.15 deg   1 passes
   ... ซ้ำ 15 ครั้ง ...
```

สาเหตุ: วงกลมรัศมี "ครึ่งความกว้างลำตัว" ที่มีจุดศูนย์กลางอยู่ที่**หัว** — ครึ่งบนของวงกลมนั้น
อยู่เหนือไหล่ขึ้นไป **คืออากาศ** เพราะที่ความสูงหัว ตัวละครแคบกว่าที่อก

**สิ่งที่ต้องจำ:** เอาจุดเล็งของรูปหนึ่ง มาจับคู่กับขนาดของอีกรูปหนึ่งที่อยู่คนละตำแหน่ง
= ช่องว่างระหว่างสองรูปนั้นคือที่ที่ความผิดพลาดไปกอง **และมันเงียบ** — ระบบรายงานว่าสำเร็จทุกครั้ง

**บทเรียนที่กว้างกว่า:** เกณฑ์ที่บอกว่า "พอแล้ว" ต้องอธิบายด้วยรูปเดียวกับที่ใช้ตั้งเป้า
ถ้าอธิบายด้วยคนละรูป มันจะถูกตรงกลางและผิดที่ขอบเสมอ

**E9 — เกณฑ์ที่หยุดการเข้าใกล้ คือจุดจอด ไม่ใช่ขีดจำกัด**

ตั้งไว้ว่า "พอเข้าเขตตัวเป้าแล้วปล่อย" โดยคิดว่าเขตนั้นคือ**ขอบเขตที่ยอมรับได้**
แต่การดึงลดระยะห่างลงทีละส่วนแล้ว**หยุดทันทีที่เข้าเขต** — pass สุดท้ายจึงพาจาก
~1.5 เท่าของเขต มาเหลือ ~0.95 เท่า **มันจอดที่ขอบเสมอ ไม่เคยเข้าใกล้กลาง**

วัดจาก log ได้ชัด — ส่งมอบ 68 ครั้ง:

```
 6u  8u  8u  8u  9u  9u 10u 10u 10u 11u 11u 11u 12u ...
median 10u จากเขต 12u
```

ตั้งเขตไว้เท่ากับครึ่งความกว้างลำตัว = **จอดบนเส้นขอบลำตัวทุกครั้ง** ซึ่งคือไหล่หรือแขน

**สิ่งที่ต้องจำ:** เกณฑ์ที่ใช้หยุดกระบวนการที่เข้าใกล้ทีละนิด **ไม่ใช่ "ห่างได้มากสุดเท่าไหร่"
แต่คือ "จะจอดห่างเท่าไหร่"** ตั้งชื่อและตั้งค่าตามความหมายหลัง ไม่ใช่ความหมายแรก

**เกี่ยวกับชื่อด้วย:** ตัวแปรเดิมชื่อ "ครึ่งความกว้างลำตัว" ซึ่ง**อธิบายที่มาของตัวเลข
ไม่ได้อธิบายหน้าที่ของมัน** ชื่อแบบนั้นทำให้ตั้งค่าผิดโดยที่อ่านโค้ดแล้วดูสมเหตุผททุกบรรทัด

### รูปแบบความล้มเหลวที่ต้องระวังตั้งแต่แรก

> **กฎเปลี่ยน → เงื่อนไขกลายเป็นค่าคงที่ → ส่วนที่อยู่ใต้มันตายเงียบ → ไม่มีอะไรแจ้งเตือน**

เกิดกับของเดิม 2 ครั้ง ครั้งหนึ่งไม่มีใครรู้อยู่ 15 เวอร์ชัน

**ราคาถูกที่สุดในการกัน: ทุกเงื่อนไขที่ตัดสินใจมีตัวนับของตัวเอง และตัวนับที่ไม่เคยขยับ
คือการค้นพบ ไม่ใช่ความเงียบ** — เริ่มทำตั้งแต่ขั้นที่มีเงื่อนไขแรก

### สิ่งที่โปรดักต์เดิมทำถูกและควรรักษาไว้

- **ไม่มีเครื่องหมายงานค้างเลยสักตัวทั่วทั้งโปรเจกต์** — ไม่ทิ้งปัญหาที่รู้แล้วไว้โดยไม่บันทึก
- **หลักฐานมาก่อนการแก้** — อย่าแก้บนสมมติฐาน สาเหตุที่อธิบายขนาดของสิ่งที่วัดได้ไม่ได้
  คือสาเหตุที่ผิด
- **รายงานการทำนายที่ผิดตรงๆ** — การวัดที่หักล้างแผนคือผลลัพธ์ ไม่ใช่ความถอยหลัง
