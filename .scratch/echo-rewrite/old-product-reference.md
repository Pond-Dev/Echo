# Echo — ข้อกำหนดโปรดักต์

Status: ready-for-agent
สร้างเมื่อ: 2026-09-12
ขอบเขต: เขียนโปรดักต์ทั้งตัวใหม่ ทุก feature เท่าของเดิม
ฐานอ้างอิง: กฎโปรดักต์ (invariants) ที่กู้คืนมา + เอกสารอ้างอิงพฤติกรรม + เอกสารส่งมอบการ rewrite

> **คำใน glossary คงภาษาอังกฤษ** ตามที่โปรเจกต์นิยามไว้ — Aim Episode, Hold Activation,

> ตัวเลือกในเมนูก็คงภาษาอังกฤษเช่นกัน เพราะมันคือสิ่งที่ผู้เล่นเห็นบนหน้าจอ

## Problem Statement

### โปรดักต์นี้คืออะไร

เครื่องมือช่วยการยิงใน CS2 ที่รันเป็นโปรแกรมแยก อ่านสถานะเกมจากหน่วยความจำของโปรเซส
เกม แล้วทำสองอย่าง: **วาดข้อมูลทับบนจอ** และ **ส่งการขยับเมาส์เข้าไปช่วยผู้เล่น**

ปรัชญาที่คุมทุกอย่าง — **มือของผู้เล่นชนะเสมอ** ระบบช่วย ไม่ใช่ระบบเล่นแทน ทุก feature
ที่ผลิต output ถูกออกแบบให้ผู้เล่นแย่งคืนได้ตลอดเวลาโดยไม่ต้องรอ ไม่ต้องปล่อยปุ่ม
และไม่มีสถานะไหนที่ระบบ "ยึด" เอาไว้

### ทำไมต้องเขียนใหม่

โปรดักต์เดิมทำงานถูกต้องในรอบจริง แต่แก้ต่อไม่ได้ในความเร็วที่ต้องการ

> **ข้อความส่วนนี้เขียนใหม่หลังอ่านโมดูลตัดสินใจทั้งหมดจริง (5,185 บรรทัด)**
> บัญชีเต็มอยู่ใน `harvest.md` — ข้อสรุปเดิมที่ว่า *"defect คือ function ก้อนเดียวมหึมา"*
> **ไม่ถูก** และการเชื่อตามนั้นจะทำให้ rewrite ทำงานผิดจุด

### สิ่งที่ดีอยู่แล้ว และห้ามแตะ

การอ่านจริงพบว่ากระดูกของโปรดักต์เดิมถูกต้อง:

- **การแบ่ง 8 phase ถูกแล้ว** เรียงตามลำดับหลักฐานอย่างที่ควรเป็น
- **การวางกฎถูกแล้ว** เครดิตของมืออยู่ในตัววางแผน RCS · การยอมมืออยู่ในตัวควบคุม aim ·
  การลดแรงในตัวเป้าอยู่ในสถานะของ lock — **ทุกอันอยู่กับเจ้าของที่ถูกต้อง**
- **ลำดับ recoil → controller ถูกแล้ว** และมีบันทึกความล้มเหลวตอนทำกลับกันแนบไว้

**Echo ไม่ใช่ "ออกแบบโมดูลตัดสินใจใหม่" — มันคือ "เก็บสามข้อบนไว้ทั้งหมด แล้วแก้สามข้อล่าง"**

### defect จริง มีสามข้อ

**หนึ่ง — กลายพันธุ์สถานะร่วม แทนที่จะคืนตัวสืบทอด**

มี **61 จุดที่ออกจาก tick** และแต่ละจุด **รื้อสถานะคนละชุดกัน** โมดูลที่รวบรวมสูตรรื้อไว้
แชร์ได้เพียง **3 สูตร** ที่เหลือเขียนสดที่จุดเรียกและไม่ซ้ำกันเลย

หนักกว่านั้น: ตัววางแผน recoil **เดินหน้าไปแล้วตั้งแต่ก่อนตัวควบคุมทำงาน** ทุกเส้นทางที่
สุดท้ายไม่ได้ส่งแพ็กเก็ตจึงต้องย้อนมันคืน มีคอมเมนต์ในโค้ดที่ต้องอธิบายว่า
*"การย้อนกลับอยู่ห่างออกไป 50 บรรทัดและครอบไม่ถึงตรงนี้ ซึ่งเป็นเหตุผลที่เงื่อนไขที่มันคุ้มอยู่
เป็นจริงเสมอ"* — **คอมเมนต์ที่ต้องอธิบายว่าเงื่อนไขเป็นจริงเสมอ คือกลิ่นของโครงสร้างที่ผิด**

**ทั้งสองอย่างนี้คือความซับซ้อนที่เกิดจากการกลายพันธุ์ ไม่ใช่จากตัวปัญหา**
ภายใต้ตัวสืบทอดที่บริสุทธิ์ การรื้อกลายเป็น "คืนค่าที่ไม่มีของนั้น" และการย้อนกลับกลายเป็น
"ไม่รับตัวสืบทอดเข้า" — **ทั้งสองคลาสหายไปเอง**

**สอง — ไม่มีหน่วยวัดใต้ระดับ phase**

การสืบสวนจบที่ชื่อ phase เพราะไม่มีหน่วยย่อยที่มีชื่อ และผลที่ตามมาหนักกว่าการสืบสวนที่ติดขัด:
**พบกิ่งโค้ดที่ตายแล้วสองชิ้น ด้วยรูปแบบเดียวกันเป๊ะ**

```
กฎเปลี่ยน → predicate ถูกลดรูปเป็นค่าคงที่ → กิ่งใต้มันไม่เคยทำงาน
          → compiler ไม่เตือน เพราะยังเข้าถึงได้ในทางไวยากรณ์
          → ไม่มีใครรู้ (ชิ้นหนึ่งตายมา 15 เวอร์ชัน)
```

**ตัวนับต่อ guard คือดัชนีที่ถูกที่สุดที่จับรูปแบบนี้ได้** — ตัวนับที่ไม่เคยขยับใน capture จริง

**สาม — phase ผูกกับโปรเซสที่รันอยู่**

type ที่พาหลักฐานข้าม phase ถือ handle ที่ผูกกับโปรเซสเกม **หกในแปด phase จึงเรียกจาก test
ไม่ได้เลย** สิ่งที่ใช้แทนคือการ scan ข้อความ source ซึ่งพังเมื่อรัน formatter

### ความเสี่ยงตัวจริงคือความรู้ — และตอนนี้วัดขนาดได้แล้ว

ชุดเงื่อนไขที่ระบบ "ปฏิเสธที่จะทำงาน" คือความรู้ที่แพงที่สุด และการเก็บเกี่ยวพบว่ามันคือ
**61 จุด** แต่ละจุดเป็น **5 มิติ** ไม่ใช่ "เหตุผล" เดียว:

| มิติ | จำนวนค่า |
|---|---|
| ความรุนแรงระดับ session | 5 |
| จังหวะที่จะกลับมา | 5 |
| สุขภาพที่ผู้ใช้เห็น | 20 |
| ทำไมปล่อยเป้า | 11 |
| ทำไม session จบ | 14 |
| การ capture ล้มเหลวที่ไหน | 21 |

ถ้าไม่ถ่ายทอดให้ครบ จะได้ happy path ใน 2 สัปดาห์ที่รู้สึกเหมือนเสร็จ แล้วเงื่อนไขจะโผล่
ทีละข้อในรอบจริงตลอดหลายเดือนถัดมา

**ความเสี่ยงของ Echo อยู่ที่ความซื่อสัตย์ของการถ่ายทอด ไม่ใช่ที่สถาปัตยกรรม**

## Solution

### ภาพรวมระบบ

```
                      ผู้เล่น
                    │        ▲
         เมาส์จริง  │        │  ภาพบนจอ
                    ▼        │
        ┌───────────────────────────────┐
        │  Raw Input   │   Overlay+Menu │   ขอบด้าน Windows
        │  (อ่านมือ)    │   (วาด+ตั้งค่า) │
        └──────┬───────┴────────▲───────┘
               │                │
        ┌──────▼────────────────┴───────┐
        │      6 feature workers        │
        │  Aim · RCS · Trigger ·        │
        │  Nade Helper · Player Cues ·  │
        │  World (Bomb/Footsteps)       │
        └──────┬────────────────┬───────┘
               │                │
        ┌──────▼──────┐  ┌──────▼────────┐
        │ อ่านเกม      │  │  InputGate    │
        │ (ข้อเท็จจริง) │  │ (ส่งเมาส์ออก) │
        └──────┬──────┘  └──────┬────────┘
               │                │
               ▼                ▼
             โปรเซสของเกม CS2
```

**สองขอบที่มีผลจริงต่อโลกภายนอก** คือการอ่านหน่วยความจำเกม กับการส่ง input ออก
ทั้งคู่ถือเป็นขอบที่มีผลตามมา และ output ที่สร้างขึ้นทุกชนิดถูกทำให้เป็นลำดับเดียว
ผ่าน **InputGate** — ไม่มีสอง feature ส่งเมาส์พร้อมกันได้

**หลักฐานทุกชนิดเป็น fail-closed** — อัตลักษณ์, generation, แมพ, การมองเห็น, ความสด,
และการอนุญาต ทุกอันปฏิเสธเมื่อมีข้อสงสัย ความไม่แน่นอนห้ามถูกยุบเป็นความแน่นอนเพื่อ
ความสะดวก สถานะที่มีความหมาย — เห็น, ถูกบัง, ไม่มีข้อมูล, ไม่รู้ — ต้องส่งต่อครบถึงผู้บริโภค

### feature ที่มี

| # | Feature | ทำอะไร | ส่ง output? |
|---|---------|--------|-------------|
| 1 | **Aim** | ช่วยปิดมุมเข้าหาเป้าที่เลือกไว้ ขณะกดปุ่มค้าง | ✅ ขยับเมาส์ |
| 2 | **Recoil Control (RCS)** | หักล้างแรงสะท้อนของอาวุธ ไม่ผูกกับเป้า | ✅ ขยับเมาส์ |
| 3 | **Trigger** | ยิงอัตโนมัติเมื่อเล็งโดนเป้าจริง | ✅ คลิกยิง |
| 4 | **Nade Helper** | ไกด์ท่าขว้างระเบิด + ล็อกมุมมองให้ตรงท่า | ✅ ขยับ/หมุน (ผู้เล่นขว้างเอง) |
| 5 | **Player Cues** | วาดข้อมูลศัตรูทับจอ (กล่อง ชื่อ เลือด โครงกระดูก ไอคอนปืน) | ❌ วาดอย่างเดียว |
| 6 | **World** | ตัวจับเวลาระเบิด + จุดเสียงฝีเท้า | ❌ วาดอย่างเดียว |

โครงสร้างพื้นฐานร่วม: การอ่านเกม, Raw Input, InputGate, การตั้งค่า, เมนู+overlay,
การวินิจฉัย, การเริ่ม/ปิดโปรแกรม

### สิ่งที่ Echo ต่างจากของเดิม

ผู้เล่นต้องไม่เห็นความต่างเลย **ความต่างที่สังเกตได้คือข้อบกพร่อง ไม่ใช่การปรับปรุง**
สี่ข้อที่ต่างคือเรื่องภายในทั้งหมด

1. **การปฏิเสธทุกครั้งเป็นค่าที่มี type ค่าเดียว** พก basis outcome · ขั้นที่ล้ม · เหตุผลใน
   trace · **สูตรฟื้นตัว** · หลักฐานที่แนบ — ไม่ใช่การรื้อสถานะสดที่จุดเรียก
2. **seam เดียวระหว่างการอ่านเกมกับการตัดสินใจ** ทุก phase รับ snapshot ที่ test ประกอบเองได้
   และคืนตัวสืบทอด — **ไม่มีการรื้อ ไม่มีการย้อนกลับ**
3. **ทุก guard มีชื่อและตัวนับของตัวเอง** ตัวนับที่ไม่เคยขยับ = กิ่งตายที่ถูกจับได้จาก
   capture เดียว
4. **aim tick pace ด้วย deadline** คาบ = ค่าที่มากกว่าระหว่าง budget กับงานจริง

> **ข้อ 1 ไม่ใช่การประดิษฐ์ — โปรดักต์เดิมค้นพบรูปทรงนี้ไปแล้ว**
>
> การปฏิเสธของ phase `authorization` ถูกทำให้เป็นค่าที่มี type ค่าเดียวไปแล้ว พร้อมสูตร
> ฟื้นตัวห้าแบบ และ doc ของมันเขียนเหตุผลไว้ว่า *"การเก็บการจำแนกไว้ที่นี่แปลว่า
> **การปฏิเสธการพิสูจน์แบบใหม่จะไม่สามารถมีความหมายต่างกันในแต่ละจุดเรียกได้**"*
>
> มันถูกใช้กับ **1 phase จาก 8** อีก ~57 จุดปฏิเสธจำแนกตัวเองสดที่จุดเรียก ซึ่งคือสิ่งที่
> doc ของ type นั้นบอกว่าห้ามเกิด
>
> **งานของ Echo คือเอารูปทรงที่พิสูจน์แล้วนี้ไปใช้กับทั้ง 61 จุด** — ไม่ต้องเถียงเรื่อง
> รูปทรงใหม่ ไม่ต้องพิสูจน์ว่ามันได้ผล ทำไปแล้ว 1 เหลือ 7

## User Stories

### Aim

1. ในฐานะผู้เล่น ฉันอยากให้ Aim ทำงานเฉพาะตอนที่ฉันกดปุ่มของมันค้างอยู่จริง เพื่อที่จะไม่มีอะไรขยับเมาส์ตอนที่ฉันไม่ได้สั่ง
2. ในฐานะผู้เล่น ฉันอยากผูก Aim กับปุ่มเมาส์ซ้ายได้ เพื่อที่ปุ่มยิงจะเป็นปุ่มช่วยเล็งไปในตัว
3. ในฐานะผู้เล่น ฉันอยากเลือกได้ว่า Aim จับเป้าเมื่อฉันกดปุ่ม หรือเมื่อฉันเริ่มขยับเมาส์ไปทางเป้า เพื่อที่มันจะเข้ากับสไตล์การเล่นของฉัน
4. ในฐานะผู้เล่น ฉันอยากกำหนดรัศมีการจับเป้าเป็นองศาได้ เพื่อที่มันจะไม่ไปคว้าเป้าที่ฉันไม่ได้ตั้งใจเล็ง
5. ในฐานะผู้เล่น ฉันอยากให้รัศมีนั้นถูกจำกัดไว้ไม่กว้างเกินไป เพื่อที่ feature จะไม่กลายเป็นการเล่นแทนฉัน
6. ในฐานะผู้เล่น ฉันอยากปรับความเร็วในการปิดมุมด้วยปุ่มเดียว เพื่อที่ฉันจะจูนความรู้สึกได้โดยไม่ต้องเข้าใจสองค่าที่เกี่ยวพันกัน
7. ในฐานะผู้เล่น ฉันอยากให้การขยับที่ Aim ส่งออกมีจังหวะเร่ง–ลาก–เบรกเหมือนมือคน เพื่อที่มันจะไม่กระตุกเป็นก้าวเดียว
8. ในฐานะผู้เล่น ฉันอยากให้ Aim ยอมแพ้ให้มือฉัน**ตามสัดส่วนและต่อเนื่อง** เมื่อฉันฝืนไปคนละทาง เพื่อที่ฉันจะไม่ต้องสู้กับมัน
9. ในฐานะผู้เล่น ฉันอยากให้อำนาจกลับมาที่ Aim ใน tick ที่ฉันหยุดฝืนพอดี เพื่อที่จะไม่มีช่วงเงียบหรือทางลาดฟื้นตัวที่ฉันรอไม่ได้
10. ในฐานะผู้เล่น ฉันอยากให้ Aim ยังช่วยอยู่ระหว่างที่ฉันยิง เพื่อที่การช่วยจะไม่หายไปตอนที่ฉันต้องการมันที่สุด
11. ในฐานะผู้เล่น ฉันอยากให้การติดตามข้างในตัวศัตรูดำเนินต่อแบบเบาลง ไม่ใช่ดับสนิท เพื่อที่เป้าที่วิ่งสไตรฟ์อยู่จะไม่หลุด
12. ในฐานะผู้เล่น ฉันอยากให้การเข้าและออกจากตัวศัตรูไม่มีขอบเปิด–ปิด เพื่อที่มันจะไม่กระตุกที่ผิวของ capsule
13. ในฐานะผู้เล่น ฉันอยากให้การปรับมือของฉันบนตัวศัตรูถูกชั่งน้ำหนักเฉพาะจุดนั้น ไม่ถูกล็อกค้าง เพื่อที่ฉันจะขยับต่อได้ทันที
14. ในฐานะผู้เล่น ฉันอยากให้เป้าที่ผูกไว้อยู่กับฉันจนมันตาย หรือหลุดการมองเห็นเกินเวลาผ่อนผัน หรือฉันปล่อยปุ่ม เพื่อที่มันจะไม่กระโดดไปเป้าอื่นกลางคัน
15. ในฐานะผู้เล่น ฉันอยากให้การจับเป้าใหม่หลังเป้าเดิมตายเริ่มจากศูนย์ และให้มือฉันเป็นคนนำการเหวี่ยง เพื่อที่ระบบจะไม่เหวี่ยงแทนฉัน
16. ในฐานะผู้เล่น ฉันอยากให้การจบชุดยิง (นับกระสุนกลับเป็นศูนย์) ไม่ทำให้เป้าที่ผูกไว้หลุด เพื่อที่ฉันจะยิงชุดถัดไปกับเป้าเดิมได้
17. ในฐานะผู้เล่น ฉันอยากเปิดเส้นไกด์แสดงรัศมีการจับเป้าได้ เพื่อที่ฉันจะเห็นว่า Aim จะทำงานเมื่อไร
18. ในฐานะผู้เล่น ฉันอยากให้ Aim ต้องการปืนที่รองรับก่อนถึงจะทำงาน เพื่อที่มันจะไม่ทำงานตอนถือมีดหรือระเบิด

### Recoil Control

19. ในฐานะผู้เล่น ฉันอยากให้ Recoil Control เป็น lane แยกจาก Aim เพื่อที่ฉันจะเปิดมันโดยไม่เปิด Aim ได้
20. ในฐานะผู้เล่น ฉันอยากตั้งสัดส่วนการหักล้างแกนตั้งและแกนนอนแยกกันเป็นเปอร์เซ็นต์ เพื่อที่ฉันจะเลือกได้ว่าจะให้มันช่วยมากแค่ไหน
21. ในฐานะผู้เล่น ฉันอยากให้การเปิด feature ด้วยสัดส่วนศูนย์ทั้งสองแกนไม่ถูกนับเป็นความต้องการใช้งาน เพื่อที่มันจะไม่กินทรัพยากรแล้วขยับศูนย์
22. ในฐานะผู้เล่น ฉันอยากให้ Recoil Control **สนับสนุน**การดึงของฉัน ไม่ใช่บวกทับ — การที่ฉันดึงตามแรงสะท้อนต้องจ่ายหนี้การชดเชยก่อน แล้ว lane จ่ายส่วนที่เหลือ เพื่อที่เราจะไม่ดึงลงเกินพร้อมกันสองแรง
23. ในฐานะผู้เล่น ฉันอยากให้การดึงลงตามแรงสะท้อนระหว่างชุดยิงไม่ถูกตีความว่าเป็นการฝืน เพื่อที่การเล่นตามปกติของฉันจะไม่ปิด feature ไปเอง
24. ในฐานะผู้เล่น ฉันอยากให้การชดเชยของแต่ละนัดถูกจ่ายกระจายตลอดช่วงเวลาระหว่างนัด ไม่ใช่ก้อนเดียว เพื่อที่มันจะไม่กระชากเป็นจังหวะ
25. ในฐานะผู้เล่น ฉันอยากให้นัดแรกของชุดยิงถูกคิดเทียบกับความเบี่ยงเบนก่อนชุดยิง ไม่ใช่เทียบกับศูนย์ เพื่อที่การชดเชยจะตรงกับสิ่งที่เกิดขึ้นจริง
26. ในฐานะผู้เล่น ฉันอยากให้มีตัววางแผนการหักล้างตัวเดียวต่อ tick เสมอ เพื่อที่จะไม่มีการชดเชยซ้อนสองชั้น
27. ในฐานะผู้เล่น ฉันอยากให้การส่ง output ที่ถูกปฏิเสธคืนสถานะและหนี้ที่ยังไม่จ่ายกลับมา แทนที่จะทำหาย เพื่อที่การชดเชยจะไม่ขาดหายไปเงียบๆ

### Trigger

28. ในฐานะผู้เล่น ฉันอยากให้ Trigger ยิงจากการที่ Firing Ray ของมันโดนเป้าจริงเท่านั้น เพื่อที่มันจะไม่ยิงลมหรือรับเป้าต่อจาก Aim
29. ในฐานะผู้เล่น ฉันอยากให้ Trigger ทำงานเฉพาะตอนกดปุ่มค้าง เพื่อที่มันจะไม่ยิงเองตอนฉันไม่ได้สั่ง
30. ในฐานะผู้เล่น ฉันอยากให้ Trigger ปฏิเสธการผูกกับปุ่มเมาส์ซ้าย เพื่อที่มันจะไม่ขโมยปุ่มยิงของฉัน
31. ในฐานะผู้เล่น ฉันอยากตั้งเวลาหน่วงก่อนยิงได้ เพื่อที่จังหวะของมันจะดูเป็นธรรมชาติ
32. ในฐานะผู้เล่น ฉันอยากตั้งเวลาหน่วงระหว่างนัดซ้ำได้ เพื่อที่มันจะไม่รัวเกินที่ฉันต้องการ
33. ในฐานะผู้เล่น ฉันอยากให้ Trigger ยอมให้ Aim และ Nade มีสิทธิ์ก่อนเมื่อชนกัน เพื่อที่สอง feature จะไม่แย่งส่ง output กัน
34. ในฐานะผู้เล่น ฉันอยากให้ Trigger ตรวจสิทธิ์อีกครั้งภายในขอบเขตการส่งที่เรียงลำดับแล้ว เพื่อที่มันจะไม่ยิงบนหลักฐานที่เพิ่งหมดอายุ

### Nade Helper

35. ในฐานะผู้เล่น ฉันอยากเห็นเครื่องหมายในโลกบอกจุดยืนของท่าขว้างที่รู้จัก เพื่อที่ฉันจะเดินไปหาได้
36. ในฐานะผู้เล่น ฉันอยากตั้งระยะที่เครื่องหมายจะแสดงได้ เพื่อที่จอจะไม่รก
37. ในฐานะผู้เล่น ฉันอยากให้ Nade Helper เป็นไกด์เป็นหลัก และให้การล็อกมุมมองเป็นตัวเลือกเสริม เพื่อที่ฉันจะเลือกได้ว่าจะให้มันช่วยแค่ไหน
38. ในฐานะผู้เล่น ฉันอยากให้ **ฉันเป็นคนขว้างเสมอ** ระบบล็อกมุมให้ได้แต่ห้ามกดขว้างแทน เพื่อที่การตัดสินใจยังเป็นของฉัน
39. ในฐานะผู้เล่น ฉันอยากเลือกความเร็วการล็อกมุมได้สามระดับ เพื่อที่ฉันจะยังหันไปทางอื่นได้ถ้าเปลี่ยนใจ
40. ในฐานะผู้เล่น ฉันอยากให้ความเร็วสูงสุดของการล็อกยังอยู่ในระดับที่มือฉันเอาชนะได้ เพื่อที่ฉันจะไม่ติดอยู่ในมุมที่ระบบเลือก
41. ในฐานะผู้เล่น ฉันอยากให้ไกด์เลือกจุดเริ่มที่ใกล้ที่สุดที่ฉันมองเห็น เพื่อที่มันจะเสนอสิ่งที่ฉันกำลังจะทำ
42. ในฐานะผู้เล่น ฉันอยากให้ท่าที่ฉันล็อกไว้แล้วอยู่กับฉัน แม้จะมีท่าอื่นใกล้กว่าเข้ามา เพื่อที่มันจะไม่สลับกลางคัน
43. ในฐานะผู้เล่น ฉันอยากให้การเล็งไปที่จุดเริ่มอีกจุดหนึ่งย้ายไกด์ไปที่นั่นได้ เพื่อที่ฉันจะเปลี่ยนใจได้ด้วยการเล็ง
44. ในฐานะผู้เล่น ฉันอยากให้ท่ากระโดดขว้างล็อกจากพื้นที่มันถูกบันทึกไว้ เพื่อที่การล็อกจะตรงกับท่าจริง
45. ในฐานะผู้เล่น ฉันอยากให้ Nade Helper ต้องการระเบิดที่รองรับในมือก่อนถึงจะทำงาน เพื่อที่มันจะไม่กินทรัพยากรตอนฉันถือปืน
46. ในฐานะผู้เล่น ฉันอยากให้ท่าที่ใช้จุดเริ่มเดียวกันรวมเป็นเครื่องหมายเดียวที่ถือทั้งสองท่า เพื่อที่จอจะไม่มีเครื่องหมายซ้อนกัน

### Player Cues และ World

47. ในฐานะผู้เล่น ฉันอยากเลือกได้ว่าจะแสดงอะไรบ้าง — กล่อง ชื่อ แถบเลือด โครงกระดูก ไอคอนปืน ตัวจับเวลาระเบิด เสียงฝีเท้า — เพื่อที่ฉันจะเห็นเฉพาะสิ่งที่ต้องการ
48. ในฐานะผู้เล่น ฉันอยากเลือกสไตล์กล่องระหว่างเต็มกับเฉพาะมุมได้ เพื่อที่มันจะบังภาพน้อยลง
49. ในฐานะผู้เล่น ฉันอยากปรับความหนาเส้นได้ เพื่อที่มันจะอ่านออกบนความละเอียดจอของฉัน
50. ในฐานะผู้เล่น ฉันอยากตั้งระยะแสดงผลสูงสุดได้ เพื่อที่ศัตรูไกลๆ จะไม่ทำให้จอรก
51. ในฐานะผู้เล่น ฉันอยากตั้งสีของเครื่องหมายศัตรูและสีของ HUD ได้ เพื่อที่มันจะเข้ากับการมองเห็นของฉัน
52. ในฐานะผู้เล่น ฉันอยากให้เลือดถูกบอกด้วยความยาวแถบ ไม่ใช่การเปลี่ยนสี เพื่อที่ฉันจะอ่านค่าได้โดยไม่ต้องจำรหัสสี
53. ในฐานะผู้เล่น ฉันอยากให้ Player Cues ไม่คำนวณการมองเห็น เพื่อที่มันจะไม่แบกต้นทุนของสิ่งที่มันไม่ได้ใช้
54. ในฐานะผู้เล่น ฉันอยากเห็นตัวจับเวลาระเบิดเมื่อมีการวางระเบิดแล้วเท่านั้น เพื่อที่จอจะสะอาดในช่วงที่เหลือของรอบ
55. ในฐานะผู้เล่น ฉันอยากเห็นจุดที่ศัตรูเดิน เพื่อที่ฉันจะอ่านตำแหน่งจากเสียงได้แม่นขึ้น
56. ในฐานะผู้เล่น ฉันอยากให้ Player Cues, ตัวจับเวลาระเบิด และเสียงฝีเท้าไม่ติดเงื่อนไขไอเทมของ Aim, Trigger หรือ Nade เพื่อที่มันจะทำงานตอนฉันถืออะไรก็ได้
57. ในฐานะผู้เล่น ฉันอยากให้ระยะที่ตั้งไว้ถูกใช้กรองก่อนการอ่านที่แพงกว่า เพื่อที่ศัตรูนอกระยะจะไม่กินทรัพยากร
58. ในฐานะผู้เล่น ฉันอยากให้ฉากที่ไม่มีศัตรูเลยไม่รันเลนวาดอัตราเต็ม เพื่อที่ช่วงเงียบจะไม่กิน CPU

### เมนู การตั้งค่า และความเป็นส่วนตัว

59. ในฐานะผู้เล่น ฉันอยากเปิด–ปิดเมนูด้วยปุ่มที่ตั้งเองได้ เพื่อที่มันจะไม่ชนกับปุ่มในเกมของฉัน
60. ในฐานะผู้เล่น ฉันอยากให้ปุ่มที่ผูกกับ feature ไม่ทับกับปุ่มเปิดเมนู เพื่อที่ฉันจะไม่ทำตัวเองติดกับ
61. ในฐานะผู้เล่น ฉันอยากลากเมนูไปวางตรงไหนก็ได้และให้มันจำตำแหน่ง เพื่อที่ฉันจะไม่ต้องย้ายใหม่ทุกครั้ง
62. ในฐานะผู้เล่น ฉันอยากให้การตั้งค่าถูกบันทึกและอ่านกลับได้ เพื่อที่ฉันจะไม่ต้องตั้งใหม่
63. ในฐานะผู้เล่น ฉันอยากให้ไฟล์ตั้งค่าเวอร์ชันเก่าอ่านได้และเลื่อนขึ้นมาอย่างปลอดภัย เพื่อที่การอัปเดตจะไม่ล้างค่าของฉัน
64. ในฐานะผู้เล่น ฉันอยากให้ค่าที่หายไปในไฟล์เก่าถูกเติมด้วยโปรไฟล์ที่ระมัดระวัง ไม่ใช่โปรไฟล์ติดตั้งใหม่ เพื่อที่การอัปเดตจะไม่เปิด feature ให้ฉันโดยที่ฉันไม่ได้สั่ง
65. ในฐานะผู้เล่น ฉันอยากให้ค่าที่เกินเพดานในไฟล์เก่าถูกหนีบลงมาตอนโหลด เพื่อที่เพดานที่ตั้งไว้จะมีผลจริง
66. ในฐานะผู้เล่น ฉันอยากเปิดโหมดกันการถูกจับภาพหน้าจอได้ เพื่อที่ overlay จะไม่ติดไปกับการสตรีม
67. ในฐานะผู้เล่น ฉันอยากให้ log แบบละเอียดปิดอยู่โดยปริยายและเปิดได้เมื่อต้องการ เพื่อที่ไฟล์ log จะไม่บวมตอนใช้งานปกติ
68. ในฐานะผู้เล่น ฉันอยากให้มีตัวเลือก Smoke Check ตัวเดียวคุมว่าควันมีผลต่อการมองเห็นของ Aim และ Trigger หรือไม่ เพื่อที่ฉันจะไม่ต้องตั้งซ้ำสองที่

### ความปลอดภัยของ output และอำนาจของมือ

69. ในฐานะผู้เล่น ฉันอยากให้ output ที่ระบบสร้างทุกชนิดผ่านประตูเดียวที่เรียงลำดับ เพื่อที่สอง feature จะไม่ส่งเมาส์ชนกัน
70. ในฐานะผู้เล่น ฉันอยากให้ทุก feature หยุดส่ง output ทันทีที่เกมไม่ใช่หน้าต่างหน้าสุด เพื่อที่มันจะไม่ขยับเมาส์ตอนฉันสลับไปทำอย่างอื่น
71. ในฐานะผู้เล่น ฉันอยากให้เคอร์เซอร์ที่มองเห็นได้ถูกถือว่าเมนูของเกมเป็นเจ้าของเมาส์ เพื่อที่ไม่มีอะไรทำงานตอนฉันอยู่ในเมนู
72. ในฐานะผู้เล่น ฉันอยากให้สถานะเคอร์เซอร์ที่อ่านไม่ได้หรือไม่รู้จักถูกถือว่าไม่ผ่าน เพื่อที่ความไม่แน่ใจจะไม่กลายเป็นการอนุญาต
73. ในฐานะผู้เล่น ฉันอยากให้การสูญเสียสิทธิ์นั้นบังคับให้ปล่อยปุ่มและกดใหม่ก่อน Aim จะกลับมา เพื่อที่การแวะออกไปจะไม่ทิ้งล็อกที่พร้อมทำงานไว้
74. ในฐานะผู้เล่น ฉันอยากให้การสังเกตการปล่อยปุ่มครั้งเดียวไม่ถือเป็นหลักฐานว่าปล่อยจริง เพื่อที่ปุ่มที่ฉันยังกดค้างจะไม่ถูกเข้าใจผิด
75. ในฐานะผู้เล่น ฉันอยากให้การซ่อมการปล่อยปุ่มที่หายไปไม่สร้างอำนาจใหม่ให้ระบบ เพื่อที่การซ่อมจะไม่กลายเป็นการอนุญาตให้ทำงาน
76. ในฐานะผู้เล่น ฉันอยากให้การเปลี่ยนแปลงจริงของปุ่มล้างความสงสัยเรื่องการปล่อยที่หายไปก่อน เพื่อที่การกดจริงของฉันจะชนะการเดา

### ประสิทธิภาพและความไม่รู้สึกตัวของเกม

77. ในฐานะผู้เล่น ฉันอยากให้เกมไม่รู้สึกถึงโปรแกรมนี้เลย — ไม่เสีย FPS ไม่กระตุก ไม่กิน CPU ตอนอยู่เฉย
78. ในฐานะผู้เล่น ฉันอยากให้ feature ที่ปิดอยู่ไม่กินอะไรเลย เพื่อที่การปิดจะหมายถึงการปิดจริง
79. ในฐานะผู้เล่น ฉันอยากให้ feature ที่เปิดแต่ยังไม่มีงานใช้เลนความถี่ต่ำ เพื่อที่การเปิดรอจะถูก
80. ในฐานะผู้เล่น ฉันอยากให้งานหนักเกิดเฉพาะตอนที่ feature เจ้าของมันมีสิทธิ์หรือกำลังทำงานจริง
81. ในฐานะผู้ดูแล ฉันอยากให้ aim tick วิ่งถึง rate ที่ประกาศไว้จริง เพื่อที่การแก้จะลงใน tick ที่มันถูกตัดสินใจ
82. ในฐานะผู้ดูแล ฉันอยากให้ตัวเลขประสิทธิภาพรายงานเป็นการกระจายเสมอ เพื่อที่ค่ากลางที่ดูดีจะซ่อน spike ไม่ได้

### การปิดโปรแกรมและการวินิจฉัย

83. ในฐานะผู้เล่น ฉันอยากให้การปิดโปรแกรมปลุก worker ที่จอดอยู่และรอด้วยเวลาที่จำกัด เพื่อที่มันจะไม่ค้าง
84. ในฐานะผู้เล่น ฉันอยากให้ worker ทุกตัวได้โอกาสบันทึกหลักฐานสุดท้ายก่อนปิด เพื่อที่ปัญหาตอนปิดจะสืบสวนได้
85. ในฐานะผู้ดูแล ฉันอยากให้การปิดที่หมดเวลาถูกบันทึกเป็นหลักฐานที่ด้อยลง ไม่ใช่ความสำเร็จ
86. ในฐานะผู้ดูแล ฉันอยากให้ทุก feature มีร่องรอยครบตั้งแต่ความพร้อม การเริ่มทำงาน การกระทำ การปฏิเสธ จนถึงการฟื้นตัว เพื่อที่การ capture ครั้งเดียวจะพอสร้างเหตุการณ์ขึ้นใหม่ได้
87. ในฐานะผู้ดูแล ฉันอยากให้การวินิจฉัยไม่เปลี่ยนพฤติกรรมและมีขอบเขตจำกัด เพื่อที่การเปิดดูจะไม่ทำให้สิ่งที่ดูอยู่เปลี่ยนไป

### สถาปัตยกรรมและการทำงานต่อได้

88. ในฐานะผู้ดูแล ฉันอยากให้มี seam เดียวระหว่างการอ่านเกมกับการตัดสินใจ เพื่อที่จะมีจุดเดียวให้ test ทะลุผ่าน
89. ในฐานะผู้ดูแล ฉันอยากให้ทุก phase รับ snapshot แบบ owned ที่ประกอบด้วยมือได้ เพื่อที่ logic ตัดสินใจทุกส่วนจะทดสอบได้โดยไม่ต้องเปิดเกม
90. ในฐานะผู้ดูแล ฉันอยากให้ไม่มี phase ไหนเป็น function เดียว เพื่อที่การโยงต้นทุนไปที่บรรทัดจะไม่ต้องปรับโครงสร้างก่อน
91. ในฐานะผู้ดูแล ฉันอยากให้ชื่อ phase และ stage เหมือนของเดิมทุกตัว เพื่อที่ capture จากสอง codebase จะเทียบกันได้ตรงๆ
92. ในฐานะผู้ดูแล ฉันอยากให้ขอบเขตของโมดูลถูกบังคับด้วย compiler เพื่อที่การข้ามขอบเขตจะเป็น build error
93. ในฐานะผู้ดูแล ฉันอยากให้ไม่มี test ใด assert บนข้อความ source เพื่อที่การรัน formatter จะทำให้ชุด test แดงไม่ได้
94. ในฐานะผู้ดูแล ฉันอยากให้ชุด replay หนึ่งหมื่นเคสถูกยกมาและยังตรึงด้วย hash เพื่อที่การเปลี่ยนพฤติกรรมโดยไม่ตั้งใจจะโผล่ออกมาเอง
95. ในฐานะผู้ดูแล ฉันอยากให้เงื่อนไข fail-closed ทั้งหมดถูกเก็บเกี่ยวเป็นบัญชีก่อน code เดิมถูกปลดระวาง เพื่อที่มันจะไม่ต้องถูกค้นพบใหม่ในรอบจริง

## Implementation Decisions

### หลักการที่คุมทุก feature

- **มือของผู้เล่นชนะเสมอ** ทุก lane ที่ผลิต output ถูกออกแบบให้ถูกแย่งคืนได้ทันที
  ไม่มี latch ไม่มีช่วงเงียบ ไม่มีทางลาดฟื้นตัวที่ตายตัว
- **หลักฐานทุกชนิดเป็น fail-closed** อัตลักษณ์, generation, แมพ, การมองเห็น, ความสด
  และการอนุญาต ปฏิเสธเมื่อมีข้อสงสัย
- **ความไม่แน่นอนห้ามถูกยุบเป็นความแน่นอน** สถานะ เห็น / ถูกบัง / ไม่มีข้อมูล / ไม่รู้
  ต้องส่งต่อครบถึงผู้บริโภคทุกชั้น
- **การตั้งค่าคือเจตนา ไม่ใช่หลักฐานของความต้องการใช้งาน** แต่ละ feature นิยามขอบของ
  ปิดแบบถูก / เปิดแต่ว่าง / มีสิทธิ์ / กำลังทำงาน ของตัวเอง งานหนักเกิดเฉพาะสองสถานะหลัง
- **สิทธิ์เป็นของ feature ที่เป็นเจ้าของ** ไม่มีผู้บริโภคไหนรับเงื่อนไขที่ตัวเองไม่ต้องการมา
- **การจองทรัพยากรทุกครั้งมีการคืนที่คู่กัน** ผู้ใช้รายสุดท้ายเพิกถอนความพร้อมและคืน
  การถือครองทั้งหมด ธงแบบ "เคยขอแล้ว" ไม่เพียงพอ ต้องเป็น lease หรือการนับอ้างอิง
- **output ที่สร้างขึ้นทุกชนิดผ่านประตูเดียวที่เรียงลำดับ** และการอ่าน–เขียนโปรเซสเกม
  ถือเป็นขอบที่มีผลตามมา
- **เกมต้องไม่รู้สึกถึงเรา** งานร้อนใหม่ทุกชนิดต้องมีการวัดรองรับ

### Feature 1 — Aim

**ทำอะไร** ขณะที่ผู้เล่นกดปุ่มที่ผูกไว้ค้าง Aim เลือกเป้าหนึ่งตัว ผูกไว้ แล้วส่งการขยับเมาส์
เพื่อปิดมุมจากทิศที่มองอยู่ไปหาเป้านั้น

**การเปิดใช้งาน**
- Hold Activation เท่านั้น ไม่มีโหมด Always On สำหรับผู้เล่น
- ปุ่มที่ผูกได้รวมถึงปุ่มเมาส์ซ้าย — เป็นปุ่มที่ถูกต้องสำหรับ Aim (ต่างจาก Trigger ที่ต้องปฏิเสธ)
- ต้องมีปืนที่รองรับอยู่ในมือ
- ต้องมี Gameplay Mouse Input Proof: เกมเป็นหน้าต่างหน้าสุด และเคอร์เซอร์ระบบถูกซ่อน
  เคอร์เซอร์ที่มองเห็นได้ = เมนูของเกมเป็นเจ้าของ pointer, การอ่านเคอร์เซอร์ที่ล้มเหลว
  หรือสถานะที่ไม่รู้จักก็ไม่ผ่านเช่นกัน
- การสูญเสีย proof นั้นปลดเจ้าของเป้าปัจจุบัน การเคลื่อนไหว การชดเชย และสิทธิ์ Safe Entry
  แล้วบังคับให้ปล่อยปุ่มและกดใหม่

**การเลือกและผูกเป้า**
- โหมดจับเป้าสองแบบ: **On Activate** (จับตอนกดปุ่ม) และ **On Motion** (จับเมื่อผู้เล่น
  เริ่มขยับไปทางเป้า)
- รัศมีการจับเป็น half-angle ปรับได้ทีละครึ่งองศา ตั้งแต่ 0.5 ถึง **เพดาน 5 องศา**
  เพดานนี้เป็นการตัดสินใจของผู้ใช้ ตัวเลื่อนไม่เสนอค่ากว้างกว่านี้ และค่าที่บันทึกไว้เกิน
  เพดานจะถูกหนีบลงตอนโหลด
- ซองการติดตามกว้างกว่าซองการจับเป้าเสมอ
- **เจ้าของที่ผูกไว้อยู่จนกว่าจะ: มันตาย / การมองเห็นหายเกินเวลาผ่อนผัน / ปล่อยปุ่ม /
  session จบ** ไม่มีการเปลี่ยนเป้าอัตโนมัติกลางการกดค้าง ไม่มีการโอนชุดยิงอัตโนมัติ
- การจบชุดยิง (นับกระสุนกลับเป็นศูนย์) **ไม่ใช่**เหตุให้เลิกผูก มันรีเซ็ตสถานะชุดยิงเท่านั้น
- การส่ง output ที่ถูกปฏิเสธก็**ไม่ใช่** เจ้าของ การดึง generation การสะสม และจุดอ้างอิง
  การแก้รอดทั้งหมด
- หลังเป้าตาย การจับใหม่เริ่มจากศูนย์และมือของผู้เล่นเป็นคนนำการเหวี่ยง

**เรขาคณิตและการตัดสินการสัมผัส** — ทำงานบน **Core 7** capsule จริงของเป้า ไม่มีการขยาย
- **Selected Capsule** — capsule ของรูปทรงที่ผูกไว้สำหรับ Aim Episode นี้
- **Safe Entry Region** — บริเวณลึกกว่าภายใน Selected Capsule ที่พิสูจน์การสัมผัสลึก
- **Safe Entry Hold** — สถานะพร้อมก่อนยิงที่เข้าเมื่อ Control Ray ตัดกับ Safe Entry Region
- **Target Body Player-Control Zone** — บริเวณที่เกิดจาก Core 7 ที่พิสูจน์แล้ว
- การสัมผัส capsule พี่น้องเข้า Zone ได้ แต่**ไม่ใช่**การทดแทน Safe Entry ของรูปทรงที่เลือก
- นโยบายจุดเล็งถูกตรึงไว้ ไม่ใช่ตัวเลือกของผู้ใช้อีกต่อไป (สวิตช์นั้นถูกปลดตั้งแต่ schema v24)

**การส่งออกและอำนาจของมือ** — นี่คือส่วนที่กฎถูกกลับด้านจากรุ่นเก่า อ่านหัวข้อ
"ความขัดแย้งในเอกสาร" ท้ายไฟล์ก่อน
- **การช่วยระหว่างยิงได้รับอนุญาต** การนำเป้า **ไม่ถูก**ปิดตามจำนวนนัดที่ยิงไปแล้ว
  ตัวควบคุมเป้าทำงานทุก phase ยกเว้นเมื่อมี barrier ที่ประกาศชัด
- **ข้างในตัวเป้า การติดตามดำเนินต่อแบบเบา** — smoothing สูง แรงลดลง **ไม่เคยเป็นศูนย์**
  เพื่อให้เป้าที่วิ่งสไตรฟ์ยังถูกติดตาม ไม่มีขอบเปิด–ปิดที่ผิว capsule การเข้าและออกต้อง
  ไม่กระตุก การสัมผัสตัวรักษาการดึงและการสะสมของมันไว้ และผ่อนการมีส่วนร่วมลงสู่พื้น
  ที่กำหนดในช่วงเวลาสั้นๆ การออกก็ผ่อนกลับขึ้น
- **การปรับด้วยมือบนตัวเป้าถูกชั่งน้ำหนักเฉพาะจุด** ไม่ถูกล็อกค้าง ไม่เป็นขอบของการดึง
- **ยอมแพ้ให้มือตามสัดส่วนและต่อเนื่อง** ไม่มี latch ไม่มีช่วงเงียบ ไม่มีทางลาดฟื้นตัว
  การยกเลิกทั้งหมดคือการงด output หนึ่ง tick ต่อหนึ่ง tick ทั้งบนตัวและนอกตัวเป้า
  **อำนาจกลับมาใน tick ที่มือหยุดฝืนพอดี** การดึงเดิม เจ้าของ การสะสม และ generation
  ดำเนินต่อ
- โปรไฟล์การเคลื่อนที่คือ S-curve ที่จำกัด jerk — เร่ง, ลาก, เบรก
- ปุ่มปรับความเร็วมีปุ่มเดียว ค่า 1–100 ตัวควบคุมอนุมานโปรไฟล์การตอบสนองทั้งชุด
  รวมถึงทางลาดภายใน จากค่านี้ค่าเดียว

**ไกด์** — ตัวเลือกแสดงเส้นรัศมีการจับเป้า พื้นผิวนิ่ง วาดใหม่เฉพาะเมื่อ input ของการ
นำเสนอหรือวงจรชีวิตการมองเห็นเปลี่ยน

### Feature 2 — Recoil Control (RCS)

**ทำอะไร** หักล้างแรงสะท้อนของอาวุธ **ไม่ผูกกับเป้า** ทำงานเมื่ออาวุธกำลังยิง ไม่ว่า Aim
จะเปิดอยู่หรือมีเป้าหรือไม่

**ตัวเลือก** — สวิตช์หลัก + สัดส่วนแกนตั้งและแกนนอน แยกกัน 0–100 เปอร์เซ็นต์
สวิตช์หลักลำพังไม่ใช่ความต้องการใช้งาน: lane ที่ชดเชยศูนย์ทั้งสองแกนจะจ่ายต้นทุน worker
แล้วขยับศูนย์ ต้องมีอย่างน้อยหนึ่งแกนมากกว่าศูนย์

**หนึ่ง lane ต่อหนึ่ง tick เสมอ**
- Aim ล็อกอยู่ → ตัววางแผนการหักล้างทำงาน**ข้างใน** aim lane ในรูป feedforward
- Aim ปิด → ทำงานแบบ**ยืนเดี่ยว**
- **ไม่มีทางที่จะมีตัววางแผนสองตัวบน tick เดียว** วัดแล้ว: เมื่อมือผ่อน aim lane เพียงลำพัง
  เหลือความคลาดเคลื่อนราวหนึ่งในสี่องศา ซึ่งตรงกับที่วัดได้บนนัดที่เข้าจริง การซ้อน lane
  ที่สองทับจึงชดเชยเกินเป็นสองเท่า
- tick ที่ Aim เป็นเจ้าของจะปลดฐานการหักล้างที่ตัวเองไม่ได้สังเกต

**การจ่ายหนี้การชดเชย**
- ทุกขอบของนัดยิง การเปลี่ยนแปลงของแรงสะท้อนถูกลงบัญชีทันทีทั้งก้อน แล้ว**จ่ายกระจาย
  ตลอดราวแปดสิบเปอร์เซ็นต์ของช่วงเวลาระหว่างนัด ไม่เคยจ่ายในแพ็กเก็ตเดียว**
- ตัวควบคุมถูกแสดงทิศทางอย่างที่มันจะเป็นเมื่อหนี้ทั้งก้อนถูกจ่ายครบแล้ว และมันไล่ตาม
  เป้าเท่านั้น
- **การดึงของผู้เล่นตามแนวแรงสะท้อนจ่ายหนี้ก่อน** lane จ่ายส่วนที่เหลือ — หลักคือ
  ผู้เล่นดึงอยู่แล้วเสมอ ระบบมีไว้ช่วย การดึงที่ทำก่อนขอบนัดถัดไปถูกเก็บเป็นเครดิตที่มี
  ขอบเขตต่อหนึ่งชุดยิง
- **การดึงลงตามแรงสะท้อนระหว่างชุดยิงคือการสนับสนุน ไม่ใช่การแย่ง** มันไม่ถูกจัดเป็น
  การฝืนและไม่ล็อกการยอมแพ้ ไม่ว่าการแก้เป้าใน tick นั้นจะชี้ไปทางไหน
- นัดแรกของชุดยิงถูกลงบัญชีเทียบกับความเบี่ยงเบนก่อนชุดยิงที่ lane เฝ้าดูอยู่ ไม่ใช่เทียบศูนย์
- **RCS ไม่ยอมแพ้ให้การฝืน** (ต่างจาก Aim) แต่มัน**สนับสนุน**มือแทนที่จะบวกทับ
- การส่งที่ถูกปฏิเสธคืนฐานและหนี้ที่ยังไม่จ่ายให้ตัววางแผน แทนที่จะทำการเปลี่ยนแปลงนั้นหาย

**การรีเซ็ตแบบแรง** เกิดจากสี่เหตุที่แยกประเภทได้: เปลี่ยนอาวุธ, ตัวนับนัดถอยหลังแบบไม่ใช่
ศูนย์, จบชุดยิง, และการย้อนจากชุดยิงกลับไปนัดแรก ทุกเหตุข้ามผ่านกำแพงรีเซ็ตที่ตรวจว่า
output เป็นศูนย์แล้ว ก่อนฐานใหม่จะถูกยอมรับ — **ไม่ใช่การส่งแพ็กเก็ตคลายกลับ**

### Feature 3 — Trigger

**ทำอะไร** ยิงอัตโนมัติเมื่อ Firing Ray ของมันเองสัมผัสเป้าจริง

**กฎการสัมผัส** — สัมผัสเท่านั้น ไม่มีการส่งต่อเป้าจาก Aim ไม่มีการรอปุ่มร่วมกัน
การยิงทะลุกำแพงที่รองรับอยู่แล้วยังคงไว้ **งานด้านเวลา ความสด หรือการวินิจฉัยห้าม
ขยายเซตของเป้าที่มีสิทธิ์อย่างเงียบๆ** การขยายนโยบายต้องผ่านการอนุมัติของผู้ใช้อย่างชัดเจน

**การเปิดใช้งาน** — Hold เท่านั้น ไม่มีโหมด Always On ไม่มีในโครงสร้างการตั้งค่า
ไม่มีในเมนู และค่าที่บันทึกไว้เป็น Always On จะถอดรหัสกลับมาเป็น Hold
**Trigger ปฏิเสธการผูกกับปุ่มเมาส์ซ้าย** — ห้ามขโมยปุ่มยิงของผู้เล่น

**เวลา** — ตั้งหน่วงก่อนยิงและหน่วงระหว่างนัดซ้ำได้แยกกัน

**ลำดับความสำคัญ** — สถานะที่ถูกบล็อกด้วยการถือครอง output ของ Nade หรือสิทธิ์ก่อนของ Aim
ใช้เลนที่ไม่ทำงานแบบมีขอบเขต **ห้ามคงจังหวะการตรวจสัมผัสแบบทำงานอยู่** เมื่อผูกคนละปุ่ม
การกดค้างของ Aim ทำให้ Aim ได้สิทธิ์ก่อน; การผูกปุ่มเดียวกันไม่ทำให้ Trigger รอ Aim

**ก่อนส่ง** ยังต้องมีความพร้อมของอาวุธ ความสดของหลักฐาน การมองเห็น การอนุญาตขั้นสุดท้าย
และการส่งผ่านประตูที่เรียงลำดับ โดย**ตรวจสิทธิ์อีกครั้งภายในขอบเขตการส่งนั้น**

**หลักฐานเชื่อมโยงนัดยิง** เป็นตัวเลือกสำหรับการดีบั๊ก ผูกรหัสนัดหลังธุรกรรมสำเร็จครบ
แล้วคลี่ผลออกจากการสังเกตตารางการยิงของอาวุธเดียวกันที่มีอยู่แล้ว — เป็นการรับรู้ที่
เชื่อมโยงได้, หมดเวลา, รับรู้ช้า, เปลี่ยนอาวุธ, ถูกการส่งใหม่แทนที่ หรือขอบของ session
**การรับรู้ของอาวุธไม่ใช่ข้อพิสูจน์ว่าคลิกที่ฉีดเข้าไปทำให้เกิดนัดยิงหรือความเสียหายจริง**
แหล่งที่มาของการโดนยังคงระบุชัดว่าไม่มีข้อมูล จนกว่าจะมีหลักฐานความเสียหายที่เชื่อถือได้

### Feature 4 — Nade Helper

**ทำอะไร** เป็นไกด์เป็นหลัก แสดงจุดยืนและท่าขว้างที่รู้จักบนแมพปัจจุบัน และช่วยล็อกมุมมอง
ให้ตรงกับท่านั้นได้ถ้าผู้เล่นเปิดตัวเลือกไว้

**หลักที่ไม่เปลี่ยน — ผู้เล่นเป็นคนขว้างเสมอ** การล็อกมุมมองเป็นตัวควบคุมเดียวที่ผลิต
output ได้ และ output นั้นคือการเคลื่อนที่และการแก้มุมมองที่มีขอบเขตเท่านั้น
**ไม่มีการกดขว้างแทน โดยเจตนา**

**ตัวเลือก** — สวิตช์หลัก, ล็อกมุมมองอัตโนมัติ, แสดงเครื่องหมายในโลก, ระยะของเครื่องหมาย,
และความเร็วการล็อกสามระดับ สวิตช์หลักลำพังไม่ใช่ความต้องการใช้งาน: ต้องมีผู้บริโภคลูก
อย่างน้อยหนึ่งตัว (เครื่องหมายหรือการล็อก) ถูกเลือก

**ความเร็วการล็อกแสดงเป็นอัตราจริงขององศาต่อวินาที** ไม่ใช่น้ำหนักทึบ เพราะนั่นคือสิ่งที่
ผู้เล่นต้องหมุนชนะถ้าอยากเล็งไปทางอื่นขณะล็อกอยู่ **เพดานถูกตั้งไว้ให้มือยังเอาชนะได้**
การยกให้สูงกว่านี้ทำให้การล็อกเอาชนะด้วยมือไม่ได้

**การเลือกท่า**
- ไกด์ติดตามจุดเริ่มที่ใกล้ที่สุดที่มองเห็น
- session ที่ถูกปักไว้แล้วรักษาท่าของมันไว้แม้จะมีคู่แข่งที่ใกล้กว่าเข้ามา
- การเล็งไปที่จุดที่สองย้ายไกด์จากจุดที่ล็อกอยู่แล้วได้
- การสั่นของตำแหน่งระดับต่ำกว่าหนึ่งหน่วยห้ามพลิกท่าที่เลือกไว้
- ท่าที่ใช้จุดเริ่มร่วมกันตีพิมพ์เป็นเครื่องหมายเดียวที่ถือทั้งสองท่า
- ท่าที่อยู่ใกล้กันกว่าระยะขอบการสลับยังเข้าถึงได้ทั้งคู่
- ลำดับของเครื่องหมายมาจากแคตตาล็อก ไม่ใช่จากที่ที่ผู้เล่นยืน
- ทุกแถวที่มีท่ากำกับมีสิทธิ์เท่ากันทั้งสำหรับไกด์และการเดินเข้าไป
- ท่ากระโดดขว้างล็อกจากพื้นที่มันถูกบันทึกไว้
- การล็อกเมื่อไปถึงพาผู้เล่นเดินเข้าจุด **แต่ไม่ขว้างให้**

**ความต้องการใช้งาน**
- ต้องมีระเบิดที่รองรับในมือก่อนงานของ feature จะมีสิทธิ์
- ถ้าไม่มี จะรันแค่ตัวเฝ้าไอเทมและความมีชีวิตแบบมีขอบเขต แมพ แคตตาล็อก ผู้เล่น ท่า
  การสอบเทียบ Raw Input การฉาย และการวาด หยุดทั้งหมด
- ความครอบคลุมของแมพและไอเทมปัจจุบันต้องพิสูจน์ก่อนงานละเอียด ความครอบคลุมที่รู้ว่าขาด
  จะเหลือแค่ตัวเฝ้าการฟื้นตัวแบบมีขอบเขต
- Nade เป็นเจ้าของความต้องการ Raw Input จากเส้นทางสิทธิ์ขั้นสุดท้ายและการควบคุมของตัวเอง
- session การจัดแนวที่ยังมีชีวิตรักษาความต้องการ Raw Input ไว้ไม่ว่าสถานะการแสดงผลจะเป็นอย่างไร
  จนกว่า lease ของ output จะถูกคืน
- **ความต้องการ Raw Input ที่ยังค้างอยู่ห้ามติดอาวุธให้ output**
- ทุกการตีพิมพ์ทั้งช่วงต้นและช่วงสุดท้ายกระทบยอดการถือครองความต้องการ Raw Input ในรอบเดียวกัน
- สถานะ Nade ที่ไม่เปลี่ยนซ้ำๆ ใช้การถือครองแมพ ป้าย และเครื่องหมายเดิมที่ไม่เปลี่ยนแปลงซ้ำ

### Feature 5 — Player Cues

**ทำอะไร** วาดข้อมูลศัตรูทับบนจอ **ไม่ผลิต output ใดๆ**

**องค์ประกอบที่เลือกเปิดได้เจ็ดอย่าง** — Box, Name, Health Bar, Skeleton, Weapon Icon,
Bomb Timer, Footsteps

**การตั้งค่าการแสดงผล**
- สไตล์กล่อง: เต็ม หรือ เฉพาะมุม
- ความหนาเส้น 1–4 พิกเซล
- ระยะแสดงผลสูงสุด ปรับเป็นขั้นละห้าเมตร
- สีของเครื่องหมายศัตรู และสีของ HUD

**Player Cues ไม่คำนวณการมองเห็น** จึงมี**สีเดียว** ไม่มีสีที่สองให้สลับ และ**เลือดถูกบอก
ด้วยความยาวแถบ** นี่เป็นการตัดสินใจเชิงต้นทุน: การมองเห็นเป็นการคำนวณที่แพงและ feature
นี้ไม่ได้ใช้มัน

**กฎด้านความต้องการใช้งาน**
- สวิตช์หลักเปิด feature แต่ถ้าไม่มีองค์ประกอบใดถูกเลือกเลย ก็ไม่มีการสแกน การฉาย
  หรือการวาดให้บริการ
- **ระยะที่ตั้งไว้ถูกใช้กรองตั้งแต่ตัวอย่างอัตลักษณ์ สถานะชีวิต และจุดกำเนิด — ก่อน**
  การอ่านหัวหรือชื่อ และก่อนการสร้างหลักฐานของ Skeleton หรืออาวุธ
- ฉากค้นพบที่ว่างเปล่าห้ามรันเลนการนำเสนออัตราเต็ม และห้ามถือแคตตาล็อกโมเดลหรืออุปกรณ์
  ไว้เกินเวลาผ่อนผันกันการสั่นที่มีขอบเขต
- **ESP กำหนดจังหวะของตัวเองโดยไม่อ่านสถานะของ feature อื่น**
- Player Cues, Bomb Timer และ Footsteps **ห้ามรับเงื่อนไขไอเทมของ Nade, Aim, Trigger
  หรือไกด์ FOV ของ Aim มา**

### Feature 6 — World: Bomb Timer และ Footsteps

**Bomb Timer** — นับเวลาถอยหลังเมื่อมีการวางระเบิดแล้ว
- ห้ามรับจุดยึดของผู้เล่นท้องถิ่นที่ตัวเองไม่ได้ใช้มา — **โดยไม่ทำให้การพิสูจน์ทีมและ
  จุดกำเนิดที่การสแกนศัตรูและเสียงฝีเท้าต้องการอ่อนลง**
- เมื่อยังไม่มีการวางระเบิด งานโลกและการนำเสนอเฉพาะวัตถุประสงค์อยู่บนเลนความหมายอัตราต่ำ

**Footsteps** — แสดงจุดที่ศัตรูเดิน จากการสะสมการเคลื่อนที่ในแนวระนาบ
- ปล่อยเหตุการณ์ที่ตำแหน่งปัจจุบันเมื่อการเคลื่อนที่สะสมถึงเกณฑ์
- จุดกำเนิดที่อยู่นิ่งไม่ปล่อยก้าวโดยประมาณ
- การกระโดดข้ามตำแหน่งและความไม่ต่อเนื่องในแนวดิ่งรีเซ็ตการสะสม
- ตัวตรวจไม่ข้ามการเปลี่ยนอัตลักษณ์หรือช่องว่างที่หลักฐานเก่าเกิน
- จังหวะที่เร็วเกินถูกกดครั้งเดียว และ**การกดนั้นห้ามเลื่อนหน้าต่างกันสั่น**
- ประตูระยะกินจังหวะไปหนึ่งครั้งโดยไม่ปล่อยเหตุการณ์
- งานพื้นและการมองเห็นแบบสถิตต้องการผู้สมัครที่อยู่ในระยะ เครื่องหมายที่ยังมีชีวิต หรือ
  เวลาผ่อนผันกันการสั่นที่มีขอบเขตและบันทึกไว้

### เมนู การตั้งค่า และ overlay

- **เมนูเปิด–ปิดด้วยปุ่มที่ตั้งเองได้** และปุ่มที่ผูกกับ feature ต้องไม่ทับกับมัน
- เมนูลากวางได้และจำตำแหน่ง
- การตั้งค่าถูกบันทึกเป็นไฟล์ที่มี schema เป็นเวอร์ชัน และเลื่อนเวอร์ชันขึ้นได้
- **โปรไฟล์สำหรับกรณีไม่มีข้อมูลต้องเป็นโปรไฟล์ที่ระมัดระวัง ไม่ใช่โปรไฟล์ติดตั้งใหม่**
  โปรไฟล์ติดตั้งใหม่เปิด feature การยิงไว้ทุกตัว การใช้มันแทนค่าที่หายไปจะเท่ากับ
  เปิด feature ให้ผู้ใช้ลับหลังตอนอัปเกรด และจะวาดเมนูเหมือน feature กำลังทำงานอยู่
  ทั้งที่ยังไม่ได้อ่านอะไรเลย
- ค่าที่เกินเพดานถูกหนีบลงตอนโหลด
- **โหมดกันการถูกจับภาพหน้าจอ** เปิดได้
- **log แบบละเอียดปิดโดยปริยาย** เปิดเมื่อต้องดีบั๊ก
- overlay ไม่อ่านหน่วยความจำเกมเอง — มันบริโภคการตีพิมพ์ที่มีขอบเขตจากผู้ผลิต
- การตีพิมพ์ภาพที่เทียบเท่ากันรีเฟรชความสดโดยไม่จองสำเนาใหม่
- ผู้ผลิตฉากในเกมเคารพหลักฐานความต้องการการนำเสนอที่สดและผูกกับอัตลักษณ์ของโปรเซส
  หน้าสุดอย่างเจาะจง และเพิกถอนกล้อง แคตตาล็อก แมพ การมองเห็น และ input เมื่อเป้าหมาย
  ไม่ใช่พื้นผิวเกมที่อยู่หน้าสุด หรือเมนูเป็นเจ้าของ focus หรือหลักฐานเก่าเกิน

### โครงสร้างพื้นฐานร่วม

**การอ่านเกม** — ผลิตข้อเท็จจริงที่มีชนิด ผ่านการ capture แบบเป็นขั้น พร้อมตารางออฟเซ็ต
แคตตาล็อกทรัพยากร เรขาคณิตของโมเดล และการ ray trace การมองเห็นของตัวเอง (เกมไม่ทำให้)
รวมถึงการแปลงองศาเป็นจำนวนนับของเมาส์ที่สอบเทียบแล้ว

**ข้อจำกัดลำดับการอ่านที่ต้องรักษา** — ลำดับ bracket ภายในด้านตัวอย่างเดียวคือ
"ไม่หลังจาก" ไม่ใช่ "ก่อนอย่างเคร่งครัด" หน้าต่างใดที่ถูกขยายต้องรักษาให้การสุ่ม
**อัตลักษณ์ดิบเป็นการอ่านสุดท้ายของทุกเป้า** และรักษาตัวอย่างชุดโมเดลทั้งสองให้มีชีวิต
ต่อหนึ่งรอบ

**Raw Input** — อ่านเมาส์จริงของผู้เล่น
- **การสังเกตการปล่อยปุ่มแบบอะซิงโครนัสครั้งเดียวไม่ใช่ข้อพิสูจน์ว่าการปล่อยหายไป**
- การถือว่าการปล่อยหายไปต้องมีการยืนยันที่ไม่เปลี่ยนแปลงในภายหลัง หรือหลักฐานเชิงลำดับ
  ที่เทียบเท่า
- การเปลี่ยนแปลงจริงใดๆ ล้างความสงสัยเรื่องการปล่อยที่หายไปก่อนการซ่อมสังเคราะห์จะดำเนินต่อได้
- **การซ่อมการปล่อยแบบสังเคราะห์ไม่สร้างอำนาจใหม่ให้ผู้เล่น**
- การนับการเปลี่ยนสถานะการกดระหว่างสอง tick เป็นข้อพิสูจน์การปล่อยสำหรับทั้งตัวเฝ้าที่ว่าง
  และ session
- Aim ถือตัวรับ Raw Input แบบขับด้วยเหตุการณ์ขณะไม่ทำงานได้ เพื่อไม่ให้การกดสั้นๆ หายไป
  โดยสถานะพักไม่ถือครองงานการเคลื่อนไหวหรือสิทธิ์ output ใดๆ

**InputGate** — ประตูเดียวที่เรียงลำดับสำหรับ output ที่สร้างขึ้นทั้งหมด
- lease สุดท้ายเพิกถอนความพร้อมแบบซิงโครนัสก่อนกลับสู่สถานะพัก
- ความต้องการ output ที่มีขอบเขตครั้งแรกปลุกผู้ผลิตทันที และอยู่ในสถานะปฏิเสธไว้ก่อน
  จนกว่าการตรวจสอบตัวเองของการลงทะเบียน Raw Input จะรับรอง generation เดียวกัน

**การประสานทรัพยากร** — เป็นเจ้าของความต้องการ, generation ของ session, การฟื้นตัว
และการปลดระวาง
- ทรัพยากรร่วมใช้ lease แบบมีขอบเขตหรือความต้องการแบบนับอ้างอิง
- **สินทรัพย์ที่ไม่เปลี่ยนแปลงที่ถือไว้จะถูกใช้ซ้ำได้ก็ต่อเมื่อการใช้ซ้ำนั้นไม่ถือครองสิทธิ์
  ที่ทำงานอยู่ และทุกอัตลักษณ์ generation input และความสดที่ผู้บริโภคต้องการถูกตรวจใหม่**
- **generation ที่ค้างอยู่หรือเก่าเกินห้ามอนุญาต output** การฟื้นตัวต้องการหลักฐานปัจจุบัน
  ธงที่บอกว่าเก่าหรือการสังเกตคลุมเครือครั้งเดียวไม่คืนอะไรเลย

**การเริ่มและปิดโปรแกรม**
- การปิดทำให้สิทธิ์ของ session ร่วมเป็นโมฆะ ปลุก worker ที่จอดอยู่ แล้วรอด้วยเครื่องกั้น
  ที่ลงทะเบียนไว้และมีขอบเขตเวลา
- worker ที่เริ่มแล้วทุกตัวได้โอกาสปล่อยหลักฐานสุดท้ายหรือหลักฐานบางส่วน ก่อนการล้าง
  log ครั้งสุดท้าย และการล้างนั้นเกิดหลังจากการทำให้เป็นโมฆะ การปลุก และเครื่องกั้น
  คลี่คลายแล้วเท่านั้น
- **การปิดที่หมดเวลาคือหลักฐานที่ด้อยลง ไม่ใช่ความสำเร็จ**

**การวินิจฉัย**
- ทุก feature มีความครอบคลุมที่ดูแลไปพร้อมกับตัว feature และมีสัญญาร่องรอยสำหรับวงจร
  ชีวิตของมัน
- ความครอบคลุมทำให้เส้นทางความพร้อม การเริ่มทำงาน การกระทำ การปฏิเสธหรือความล้มเหลว
  การฟื้นตัว และการปิด สังเกตได้
- **feature ที่ยังมีเส้นทางเงียบอยู่ถือว่ายังไม่เสร็จ**
- capture สดครั้งเดียวต้องพอให้ผู้ตรวจสร้างเหตุการณ์ขึ้นใหม่ได้ตั้งแต่ session/build/settings
  → การเริ่มทำงาน/input → การเปลี่ยนสถานะ → หลักฐาน → การอนุญาต → การพยายามกระทำ
  → ผลของการกระทำ → การฟื้นตัว
- **การวินิจฉัยสังเกตขอบที่มีผลตามมาได้ แต่ต้องมีขอบเขตและไม่เปลี่ยนพฤติกรรม**
  เว้นแต่มีการอนุมัติการเปลี่ยนพฤติกรรมอย่างชัดเจน
- เมื่อสาเหตุที่เป็นไปได้แยกจากกันไม่ออก ให้เพิ่มการวินิจฉัยที่มีชนิด มีขอบเขต และไม่เปลี่ยน
  พฤติกรรม แล้ว capture — **ก่อน**เปลี่ยนพฤติกรรม

### Aim tick pipeline

**แปด phase หลัก ตามลำดับการทำงาน:** readiness → activation → stage tick →
retained revalidation → selection → authorization → controller step → commit

**สิบสี่ sub-phase** จัดกลุ่มอยู่ใต้สามตัวนี้
- ใต้ retained revalidation: local frame, local slot, flash, candidate control, owner status
- ใต้ authorization: opening control, view, visibility local, visibility query,
  closing control, target status
- ใต้ commit: gate view, gate control, target status

**สิบเก้า stage ของ staged capture** ครอบตั้งแต่การสแกนระเบียน การสร้างผังการครอบครอง
การเปรียบเทียบ การตรวจซ้ำที่ค้างอยู่ การสร้าง output การทำให้เป็นมาตรฐาน ผังการพิสูจน์
การตรวจ Core 7 การผูกหลักฐาน จนถึงการสุ่มอัตลักษณ์เป้า การค้นหาโมเดล ช่วงการแปลง
และการสร้าง capsule

**ชื่อเหล่านี้คือสัญญา** Echo ต้องใช้ชื่อเดียวกันทุกตัว เพราะนั่นคือสิ่งเดียวที่ทำให้ capture
จาก Echo กับจาก build เดิมเทียบกันได้ — ซึ่งเป็นหลักฐานเดียวที่มีว่า Echo ดีกว่าจริง

**ต่อขั้นตอน บันทึกสี่อย่างแยกกัน**: เวลาที่ใช้, จำนวนการอ่านโปรเซส, จำนวนการจอง heap,
และไบต์ที่ขอ การยุบรวมสองอย่างแรกเข้าด้วยกันเคยกลบการหักล้างที่สำคัญมาแล้ว

**profiler ถูกตัดออกจากการ build โดยปริยาย** และ log ของ session ต้องบอกชัดว่าเปิดอยู่หรือไม่

### จังหวะของ loop

- **aim tick pace ด้วย deadline** คาบ = ค่าที่มากกว่าระหว่าง budget กับงานจริง
  fixed-delay ไม่ใช่ตัวเลือก
- การตัดสินใจนี้ยืนบนการคำนวณ ไม่ใช่การสังเกต: งานราวหนึ่งมิลลิวินาทีบนงบห้ามิลลิวินาที
  บวก overhead ของ OS ราวเก้าในสิบมิลลิวินาที อธิบายส่วนขาดของ rate ได้ทั้งหมดด้วยตัวเอง
- **rate ที่ได้ต้องถูกวัดใน Echo ก่อนจะถูกอ้าง**
- **ไม่ยกโมดูล timer ความละเอียดสูงที่เขียนเองมา** — วัดแบบ A/B ในกระบวนการเดียวกันแล้ว
  พบว่ามันเท่ากับ sleep มาตรฐานทุกช่วงเวลา รวมถึง overhead ด้วย ห้ามแตะการเปลี่ยน
  ความละเอียด timer ของระบบโดยไม่วัดก่อน

### Seam — การตัดสินใจเชิงโครงสร้างข้อเดียว

- **มี seam เดียว: การอ่านเกม กับ การตัดสินใจ** ทุก phase อยู่ใต้เส้น การอ่านเกิดเหนือเส้น
- **ทุก phase รับ snapshot ของข้อเท็จจริงแบบ owned และคืนตัวสืบทอดแบบ owned**
  เกณฑ์รับรองคือ: test ประกอบ input นี้ด้วยมือได้ไหม
- **ห้าม input ของ phase ใดถือ process handle, ตัวอ้างอิงเข้าไปในโปรเซสที่รันอยู่ หรือ
  lease ที่มีแต่ session ที่ attach อยู่เท่านั้นที่ผลิตได้** ข้อใดข้อหนึ่งเพียงลำพังก็พอ
  ที่จะทำให้ phase เรียกจาก test ไม่ได้
- **phase ที่ต้องการข้อเท็จจริงอ่านจาก snapshot ของตัวเอง** ถ้ามันต้องการสิ่งที่ snapshot
  ไม่มี วิธีแก้คือขยาย snapshot ที่ขั้นตอน capture เหนือ seam — ไม่ใช่รับ handle เข้ามา
- **ใต้ seam ไม่มี concurrency primitive ไม่มี shared mutable state และไม่มีนาฬิกา**
  เวลาเข้ามาเป็นค่าบน snapshot
- **แต่มีสถานะที่พกข้าม tick และมันเยอะ** — รูปคือ
  `(ข้อเท็จจริง, สถานะเดิม) → (ผลลัพธ์, สถานะใหม่)` ยังบริสุทธิ์ แต่ไม่ใช่ "ไม่มีสถานะ"
- **ชั้นการอ่านเหนือ seam ไม่ใช่ seam สำหรับ test และจะไม่ถูกทำให้เป็น**
  พิสูจน์ด้วย capture และ profiler **จะไม่มีการสร้าง mock ของโปรเซสเกม**

#### สถานะที่พกข้าม tick — ต้อง commit พร้อมกันหรือไม่เลย

นี่คือสิ่งที่ชุด replay ต้องครอบ และเป็นสิ่งที่ธุรกรรมหนึ่ง tick รับหรือไม่รับทั้งก้อน

| สถานะ | ประกอบด้วย |
|---|---|
| **Aim lock** | 7 สถานะ + นาฬิกา + อัตลักษณ์/generation ของ Pull Episode + **Carried Momentum (ความเร็ว *และ* ความเร่ง)** |
| **Lifecycle** | 10 การเปลี่ยนผ่าน + deadline 30 ms ของ Evidence Gap + Kill Cooldown |
| **RCS lane** | หนี้ที่ค้าง + เครดิตของมือ + ฐานที่ถือไว้ + สถานะต่อชุดยิง |
| **Spray recoil** | phase · นับนัดล่าสุด · อาวุธ · punch นัดแรก · เศษที่พก |
| **Spray delivery** | ความต่อเนื่อง + punch ที่มีผล |
| **Intent basis** | เป้า/รูปทรงที่ผูก · เซตที่ถูกบล็อก · หน้าต่างท่าทาง |
| **Motion authority** | หน้าต่าง · baseline · ตัวจำแนก |
| **Contexts** | ของตัวควบคุม · ของ gap · จุดอ้างอิงการแก้ |
| **Epochs** | control · การเริ่มต้นตัวควบคุมใหม่ · องศาต่อหนึ่งนับ |
| **ตัวล็อกความผิดพลาด** | ตัวควบคุมผิดพลาด · อาวุธไม่รองรับ · input ผิดพลาด |
| **ที่สังเกตไว้** | revision ของอำนาจ · ticket ของ output · ลำดับการกด |

**~15 ก้อน** — และ **Evidence Gap กับ Kill Cooldown ไม่มีอยู่ใน glossary หรือในเอกสารกฎเลย**
ทั้งที่เป็นกลไกกลางของการผูกเป้า ต้องเพิ่มเข้า glossary ของ Echo

#### วงเล็บมีสองชั้น ไม่ใช่ชั้นเดียว

**วงเล็บของการพิสูจน์** — พิสูจน์ → คำนวณ → พิสูจน์ใหม่ → ส่ง *(ที่รู้กันอยู่แล้ว)*

**วงเล็บของมือ** — อ่านมือ → **อ่านเกม (งานที่แพงที่สุดของ tick)** → อ่านมืออีกครั้ง
ด้วยตรรกะเดียวกันเป๊ะ เพราะมือขยับได้ระหว่างที่เรากำลังอ่านเกม

และถ้าวงเล็บเปิดตัดสินว่ามือกำลังฝืน **ทั้ง tick จบตรงนั้น ไม่ต้องอ่านเกมให้เปลือง**

> **"มือชนะเสมอ" ไม่ได้อยู่ที่ตัวประกอบตอนท้าย — มันเป็นประตูบานแรกก่อนงานที่แพงที่สุด
> จะเริ่ม** ทั้งถูกตามกฎและถูกตามต้นทุน

**หลักการที่ตามมา:** หลักฐานความปลอดภัยที่เดินหน้าทางเดียว (เช่นจำนวนนัดที่ยิงไปแล้ว)
ต้องถูกใช้ **ทั้งก่อนและหลัง** ทุกช่วงที่กินเวลานาน — ไม่งั้นนัดที่เกิดระหว่างการสแกนจะ
ทิ้งหลักฐานความพร้อมที่หมดอายุแล้วไว้ให้ใช้ต่อ

### ขอบเขตของโมดูล

- **บังคับด้วย compiler ไม่ใช่ด้วยการ scan หาชื่อ** แต่ละ stage เปิดประตูเดียว
- **ไม่มี test ใด assert บนข้อความ source ของไฟล์อื่น**
- **Echo สะอาดตาม formatter ตั้งแต่ commit แรก**

## Testing Decisions

### อะไรคือ test ที่ดี

- **assert พฤติกรรมภายนอก ไม่ใช่ implementation** ให้ snapshot ที่ประกอบขึ้นมา
  แล้ว phase ผลิตการตัดสินใจนี้
- **ไม่ต้องการเกมที่ attach อยู่** ถ้าต้องการ แปลว่า seam ถูกละเมิด — แก้ seam ไม่ใช่แก้ test
- **ไม่อ่านข้อความ source ของไฟล์อื่น**
- **ต้องแดงด้วยเหตุผลที่มันอ้าง** ก่อนรับ test ใหม่เข้า ให้ลบเงื่อนไขที่มันอ้างว่าตรึงไว้
  แล้วรันทั้งชุด: **ต้องแดงเฉพาะตัวนั้นตัวเดียว**
- **เวลาคือ input ไม่ใช่การรอ** test ที่ sleep คือ test ที่กำลังทดสอบ scheduler

### อะไรถูก test และผ่านอะไร

| สิ่งที่ test | ผ่านทาง |
|---|---|
| phase ของ pipeline | seam เดียว โดยประกอบ snapshot — ส่วนใหญ่ของชุด test |

| ตัวเฝ้าความต้องการ | input frame ที่ประกอบตรงๆ เส้นทาง reset แต่ละเส้นตรึงแยก |

| การเลือกท่าของ Nade | ตรงๆ บนแคตตาล็อกที่ประกอบขึ้น |
| ตัวตรวจ Footsteps | ตรงๆ ด้วยลำดับตำแหน่งและเวลา |

**hash ของ replay ที่เปลี่ยน = การเปลี่ยนพฤติกรรมที่ต้องมีการตัดสินใจ ไม่ใช่ test
ที่ต้องอัปเดต**

**invariant ที่ทำเครื่องหมายว่าเป็นเอกสารอย่างเดียว** ถูกแปลงเป็น test ทุกที่ที่การ
rewrite ทำให้เป็นไปได้ — เอกสาร invariants เองแย้งว่า test คือสิ่งที่ทำให้กฎมีผล

### อะไรไม่ถูก test และพิสูจน์ด้วยอะไรแทน

- **การอ่านเกม** — พิสูจน์ด้วย capture สดและจำนวนการอ่านจาก profiler
- **จังหวะของ loop และ rate ที่ทำได้** — พิสูจน์ด้วย capture รายงานเป็นการกระจาย
- **การวาดจริงบนจอ** — พิสูจน์ด้วยการดู
- **อะไรก็ตามที่โหมดความล้มเหลวเดียวคือหางของเวลา** — test มองไม่เห็น capture เห็น

### ความครอบคลุมด้านความต้องการใช้งาน

ต่อหนึ่ง feature **ควร**พิสูจน์สองทิศทาง: งานเริ่มทันทีเมื่อสิทธิ์ปรากฏ **และ**งานไม่มีอยู่
เลยเมื่อ feature ถูกปิดหรือไม่มีสิทธิ์

### การตรวจจับกิ่งที่ตายแล้ว — ข้อกำหนดใหม่ที่โปรดักต์เดิมไม่มี

โปรดักต์เดิมมีกิ่งโค้ดที่ตายแล้วสองชิ้น ชิ้นหนึ่งตายมา 15 เวอร์ชัน และไม่มีอะไรจับได้เลย
รูปแบบเหมือนกันทั้งคู่: **กฎเปลี่ยน → predicate ถูกลดรูปเป็นค่าคงที่ → กิ่งใต้มันตาย →
compiler ไม่เตือน เพราะในทางไวยากรณ์ยังเข้าถึงได้**

Echo ต้องมีสามอย่างนี้:

- **ทุก guard มีตัวนับของตัวเอง** ที่ปรากฏใน capture — ไม่ใช่แค่ตัวนับระดับ phase
- **ตัวนับที่ไม่เคยขยับตลอด session จริง คือการค้นพบ ไม่ใช่ความเงียบ** ต้องมีรายงาน
  ที่ลิสต์ guard ที่ยังไม่เคยยิงออกมาให้อ่าน
- **predicate ที่ถูกลดรูปเป็นค่าคงที่ต้องถูกทำเครื่องหมายไว้อย่างชัดเจน** พร้อมเหตุผลว่า
  ทำไมยังเก็บมันไว้ *(โปรดักต์เดิมทำถูกข้อนี้: มันเขียนไว้ว่า "เก็บเป็น predicate ที่มีชื่อ
  ไม่ inline เป็นค่าคงที่ เพื่อให้นโยบายในอนาคตมีที่เดียวที่จะเอา gate กลับมา" — แต่ไม่มีอะไร
  จับว่ากิ่งใต้มันตายไปแล้ว)*

### ตัวอย่างที่ห้ามทำตาม

- การ assert ด้วยการ scan ข้อความ source ทุกรูปแบบ
- test ใดที่ input ผลิตได้จาก session ที่ attach อยู่เท่านั้น
- รายชื่อต้องห้ามที่ใช้แทนขอบเขตที่ compiler บังคับ

## Out of Scope

- **การเปลี่ยนพฤติกรรมที่ผู้เล่นเห็น** ความต่างที่สังเกตได้คือข้อบกพร่อง ไม่ใช่การปรับปรุง
- **feature ใหม่** ไม่มีความสามารถที่ของเดิมไม่มีถูกเพิ่มระหว่างการ rewrite
- **โหมด Always On สำหรับผู้เล่น** ถูกปลดระวางไปแล้วทั้ง Aim และ Trigger ห้ามฟื้น
- **การขยายเซตเป้าที่มีสิทธิ์ของ Trigger** ต้องมีการอนุมัติของผู้ใช้เป็นเรื่องแยก
- **การกดขว้างแทนผู้เล่นใน Nade Helper** โดยเจตนา
- **การคำนวณการมองเห็นใน Player Cues** feature นี้ไม่ใช้มัน
- **การลดจำนวนการอ่านสองข้อที่ถูกปฏิเสธไว้** ยังเปิดอยู่ ต้องการการตัดสินใจใหม่
  ห้ามอ้างการปฏิเสธเก่าว่าจบแล้ว
- **การลบ lane ส่ง output ที่ตายแล้วระหว่างการ rewrite** ต้องมี capture ก่อน เพราะ
  ช่องทางข้างเคียงหนึ่งของมันป้อนเงื่อนไขการตรวจการเคลื่อนไหวซ้ำ การลบจะ**ขยาย**ชุด
  การคืนสิทธิ์ให้ผู้เล่น และเปลี่ยน tick ที่ยอมรับให้กลายเป็น tick ที่ปฏิเสธได้
  วันนี้ไม่มี test ครอบทั้งสองทิศทาง
- **การ optimise เกินกว่าการเปลี่ยนจังหวะ loop** Echo สถาปนาความสืบสวนได้ ไม่ไล่ไมโครวินาที
- **การยก timer ความละเอียดสูงที่เขียนเอง, lane ที่ตายแล้ว หรือ generic ที่มีผู้ใช้รายเดียวมา**
- **การสร้างตัวแทนทดสอบใดๆ ของโปรเซสเกม**
- **การจัดระเบียบ layer map ใหม่** มันถูกทบทวนแล้วและพบว่าใช้ได้

## Further Notes

### ⚠ ความขัดแย้งในเอกสาร ที่ต้องตัดสินก่อนเขียน Aim

พบระหว่างเตรียม spec นี้ และมันสำคัญพอที่จะทำให้เขียน Aim ผิดทั้ง feature

เอกสารอ้างอิงพฤติกรรมกับเอกสารกฎโปรดักต์ **ขัดกันตรงๆ** ในสามเรื่อง

| เรื่อง | เอกสารอ้างอิงพฤติกรรม (กฎเก่า) | เอกสารกฎโปรดักต์ (ลงวันที่ 2026-08-28) |
|---|---|---|
| การนำเป้าหลังยิงนัดแรก | **ปิด** — ทุก phase หลังยิงห้ามนำเป้า | **เปิด** — การช่วยระหว่างยิงได้รับอนุญาต ไม่ผูกกับจำนวนนัด |
| ข้างในตัวเป้า | output พุ่งเข้าเป้าเป็น **ศูนย์** | ติดตามต่อ **เบาลง ไม่เคยเป็นศูนย์** |
| การยอมแพ้ให้มือ | มีการล็อกการยอมแพ้ | **ไม่มี latch เด็ดขาด** ต่อเนื่องตามสัดส่วน |

**ผมตรวจกับ code แล้ว เอกสารกฎโปรดักต์คือของจริง** — test ทั้งสองตัวที่รับรองกฎใหม่
มีอยู่และผ่านอยู่ใน build ปัจจุบัน ตัวหนึ่งบังคับว่าการส่งต่อของ pipeline ไม่แตกกิ่งตาม
สถานะการยิงอีกแล้ว อีกตัวบังคับว่าการสัมผัสตัวเป้ารักษาการติดตามไว้ที่สัดส่วนที่ลดลง
แต่ไม่เคยเป็นศูนย์

**สาเหตุของความคลาดเคลื่อน** เอกสารกฎโปรดักต์ประกาศกลับสองคำตัดสินเก่าอย่างเป็นทางการ
แต่เอกสารอ้างอิงพฤติกรรมไม่ได้ถูกแก้ตาม การแตะเอกสารนั้นครั้งสุดท้ายเป็นเรื่องเมนู
ไม่ใช่เรื่องกฎ Aim

**สิ่งที่ต้องทำ** เมื่อยกเอกสารอ้างอิงพฤติกรรมเข้า Echo — **ห้ามยกมาคำต่อคำอย่างที่
เอกสารส่งมอบแนะนำ** สามหัวข้อที่ขัดกันต้องถูกแก้ให้ตรงกับกฎโปรดักต์ก่อน หรือไม่ก็
ต้องมีคำตัดสินใหม่ของผู้ใช้ว่าจะเอากฎไหน **นี่คือคำถามที่ต้องถามก่อนเขียน Aim บรรทัดแรก**

**ขอบเขตของข้อแรก กว้างกว่าที่เขียนไว้ตอนแรก** — เปิดนิยาม predicate จริงแล้วพบว่า
**ทั้งการนำเป้าและการจับเป้าไม่ถูก gate ตามจำนวนนัดเลยทั้งคู่** สิ่งที่ยัง gate จริง
มีเพียงสองอย่าง: **ความพร้อม Safe Entry** (ก่อนยิงเท่านั้น) และ **การส่ง spray recoil**
(ยืนยันสเปรย์แล้วเท่านั้น) มี test รับรองทั้งคู่ พร้อมเหตุผลว่า *"การนำเป้าในทุก phase
ไร้ประโยชน์ถ้าไม่จับเป้าในทุก phase"*

ดังนั้นประโยค *"ไม่มี phase หลังยิงใดที่นำเป้า จับเป้า หรือเปลี่ยนเป้าได้"* ในเอกสาร
อ้างอิงพฤติกรรม **ตายทั้งประโยค** ส่วนกฎ *"ไม่เปลี่ยนเป้าอัตโนมัติกลางการกดค้าง"*
**ยังจริง** แต่ถูกบังคับด้วยการคงเจ้าของไว้ ไม่ใช่ด้วย gate ของ phase

### 🔴 ของที่อ้างกฎที่ตายแล้ว — พบ 6 ชิ้น

| # | สิ่งที่ตาย | อยู่ที่ไหน |
|---|---|---|
| 1 | กฎ Aim เก่าสามข้อ | เอกสารอ้างอิงพฤติกรรม (สามหัวข้อ) |
| 2 | ชื่อโซนที่แปลว่า "ผู้เล่นคุมเต็ม" | glossary · ป้าย trace · ชื่อ test |
| 3 | คอมเมนต์ที่บอกว่าปุ่มเมาส์ซ้ายใช้กับ Aim ไม่ได้ | ค่าคงที่สำรองของปุ่ม |
| 4 | คอมเมนต์ *"phase หลังยิงไม่เคยนำเป้า"* | phase selection |
| 5 | **กิ่งโค้ดที่ไม่เคยทำงาน** + การวินิจฉัย 9 ฟิลด์ที่ไม่เคยยิง | phase selection |
| 6 | **lane ส่ง output ที่คำนวณแพ็กเก็ตที่ไม่มีใครส่ง 15 เวอร์ชัน** | phase controller step |

**5 กับ 6 เป็นรูปแบบเดียวกัน:** กฎเปลี่ยน → predicate ถูกลดรูปเป็นค่าคงที่ → กิ่งใต้มัน
ตายเงียบ → compiler ไม่เตือนเพราะยังเข้าถึงได้ในทางไวยากรณ์

**Echo ต้องมีวิธีจับรูปแบบนี้ตั้งแต่แรก — ตัวนับต่อ guard คือดัชนีที่ถูกที่สุด**

### 🔑 ชื่อที่แบกนโยบายไว้ คือสาเหตุที่ความขัดแย้งนี้รอดมาสามสัปดาห์

ชื่อโซนสัมผัสตัวเป้าในปัจจุบันแปลว่า *"ผู้เล่นคุมเต็ม"* ซึ่งคือกฎเก่าที่ output เป็นศูนย์
ภายใต้กฎปัจจุบันมันคือ *"โซนที่ลดแรงลงแต่ยังติดตามอยู่"* — **ไม่ใช่ผู้เล่นคุมเต็มเลย**

ปัญหาไม่ใช่ว่าชื่อเก่า แต่คือ **ชื่อเอานโยบายไปยัดไว้ในคำที่ควรเป็นข้อเท็จจริงเชิงเรขาคณิต**
ตัวโซนคือข้อเท็จจริงล้วน (*ทิศทางควบคุมอยู่ข้างในตัวที่พิสูจน์แล้ว*) ส่วน *"แล้วยังไงต่อ"*
คือกฎ ซึ่งเปลี่ยนไปแล้วหนึ่งครั้งและจะเปลี่ยนได้อีก

**Echo แยกสองอย่างนี้:** คำหนึ่งคำสำหรับข้อเท็จจริง (การสัมผัสตัวเป้า) และกฎแยกต่างหาก
ที่บอกว่าการสัมผัสนั้นลดแรงลงสู่พื้นโดยไม่ถึงศูนย์ — **กฎเปลี่ยนได้โดยไม่ทิ้งชื่อที่โกหกไว้**

เป็นเงื่อนไขนำ ไม่ใช่งานคู่ขนาน และสองข้อทำได้เฉพาะตอน build เดิมยังรันอยู่

  และหลักการออกแบบการวินิจฉัย ทั้งหมดถูกลบในการเก็บกวาดเอกสาร และ code กับบันทึก
  การตัดสินใจยังอ้างถึงสองในนั้นอยู่ **การอ้างอิงเหล่านั้นจึงชี้ไปที่ความว่างเปล่า**

- **เก็บเกี่ยวเงื่อนไข fail-closed** — ✅ **ทำไปแล้ว 5.5 จาก 6 function** ผลอยู่ใน
  `harvest.md`: **61 จุดปฏิเสธ** พร้อมเหตุผลที่โค้ดให้ไว้ · คลังคำ 6 คลัง · ของตายที่อ้าง
  กฎเก่า 6 ชิ้น · สถานะที่พกข้าม tick ~15 ก้อน · บทเรียนสามข้อข้างล่าง
  **เหลือ `commit_or_recover` (678 บรรทัด)** — ดึงจุดออกมาครบ 5 จุดแล้ว แต่ยังไม่ได้ไล่
  เหตุผลทั้งหมด มันคือวงเล็บปิดของการพิสูจน์ ต้องอ่านเต็มก่อนเขียน phase commit ของ Echo
- **เก็บ baseline ด้านประสิทธิภาพ** ถ้าไม่มี Echo จะไม่มีวันแสดงได้ว่าดีกว่า
  **ทุกความพยายามที่ผ่านมาพลาดหน้าต่างเวลา**: หน้าต่างเปิดไม่กี่วินาทีหลังไฟล์ทำงาน
  เริ่มรัน ยิงครั้งเดียว จับเวลาจากการเริ่มโปรเซสไม่ใช่จากตอน attach เข้าเกม — ผู้เล่น
  ต้องอยู่ในรอบจริงอยู่แล้วก่อนเปิดโปรแกรม session เดียวที่เคย build โดยเปิด profiling
  ไม่มีสรุป aim tick เลย **รายละเอียดราย phase ที่ข้อโต้แย้งของการ rewrite ต้องใช้
  จึงยังไม่เคยถูก capture จริงเลยสักครั้ง**

### สิ่งที่ยกมาได้เลย ไม่มีการตัดสินใจเหลือ

กฎโปรดักต์, glossary, บันทึกการตัดสินใจเชิงสถาปัตยกรรมสองฉบับ, ตารางออฟเซ็ตของเกม,
การแปลงค่า sensitivity, ตัวอ่านรูปแบบไฟล์ asset, เรขาคณิตของโมเดลที่แกะแล้ว,
ส่วนเรขาคณิตบริสุทธิ์ของจุดเล็ง, ชุด replay เรียงลำดับ, และรายการ phase/stage ของ profiler

**คัดลอกอย่างระมัดระวัง:** ส่วน Raw Input — กฎหลายข้อพึ่งพาความหมายเชิงการพิสูจน์
การปล่อยปุ่มของมัน ถ่ายทอดอย่างตั้งใจ ไม่ใช่ดัดแปลง

**เอกสารอ้างอิงพฤติกรรม:** ยกมา **หลังจาก**แก้สามหัวข้อที่ขัดกับกฎโปรดักต์แล้วเท่านั้น

### ตัวเลขที่ห้ามคำนวณใหม่

- 200 Hz คือเป้า, ~156 Hz คือที่ได้จริง, งานหนึ่ง tick ~1 มิลลิวินาที,
  การอ่านโปรเซสต่อ output tick ~940–1,000, overhead ของ sleep บน Windows ~0.9 มิลลิวินาที,
  CPU ~15% ของหนึ่งคอร์ ขณะเกมวิ่ง 125–153 FPS
- ความคลาดเคลื่อนที่ aim lane ลำพังเหลือเมื่อมือผ่อน ~0.26 องศา ตรงกับ ~0.27 องศา
  ที่วัดบนนัดที่เข้าจริง — นี่คือหลักฐานว่าทำไมห้ามมีสอง lane บน tick เดียว
- ตัวเลื่อนความเร็ว Aim: ค่าตั้งต้น 35 คือจุดปลายเร็วเดิมก่อนจะมีย่านเทอร์โบ
- เพดานความเร็วการล็อกของ Nade: 300 องศาต่อวินาที ที่ sensitivity 0.9 เท่ากับราว
  15,000 นับเมาส์ต่อวินาที — สูงกว่านี้ผู้เล่นเอาชนะด้วยมือไม่ได้

### 🔴 บทเรียนสามข้อที่ต้องยกเข้า Echo คำต่อคำ

เจอจากการอ่านโมดูลตัดสินใจ ทั้งสามข้อเป็น *อาการ → การวัด → สาเหตุ → การแก้* ที่ครบ
และเป็นสิ่งที่ไม่มีทางได้กลับคืนจากการอ่านโค้ดที่มันผลิตขึ้น

**หนึ่ง — ทำไม recoil ต้องวางแผนก่อนตัวควบคุม**

> *"สองอย่างผิดพลาดตอนที่พับมันเข้ามาหลังตัวควบคุมครั้งแรก: error ของตัวควบคุมมีขั้น punch
> อยู่แล้ว การยกเลิกขั้นนั้นในแพ็กเก็ตเดียวกันจึงชดเชยสองเท่าและ tick ถัดมาเหวี่ยงกลับ
> และตัววางแผนยังไล่ตามการสลายตัวของสปริงกล้องระหว่างนัดด้วย — ฟันเลื่อยที่อัตราการยิง
> รวมกันแล้วผู้รายงานเห็นภาพสั่น"*

ปัจจุบันตัววางแผนทำงานเฉพาะที่ขอบของนัด และตัวควบคุมประเมินเรขาคณิตของมันกับทิศทางที่
ถูกถือไว้หลังการชดเชยแล้ว — **สิ่งที่มันไล่ตามจึงมีแค่เป้าเท่านั้น**

**สอง — ทำไม Player Override ที่ขอบของการกดถูกถอดออก**

> *"การจำแนกการเคลื่อนไหวที่ผู้เล่นกำลังทำอยู่ว่าเป็นการแย่งคืน แปลว่าการกดขณะที่มือกำลัง
> ขยับ — **ซึ่งคือสิ่งที่ผู้เล่นทุกคนทำ** — ข้ามทั้ง tick และไม่เกิดการดึงเลย
> log แสดงว่ามันยิงประมาณ **6 ครั้งต่อการเล่นทุก 30 วินาที** และมันคือรายงาน
> **"กดแล้วไม่มีอะไรจับ""*

การขัดแย้งโดยเจตนาถูกชั่งน้ำหนักทีละ tick ในระหว่าง lock ที่ตั้งมั่นแล้วแทน

**Echo ห้ามเอา Player Override ที่ขอบของการกดกลับมา** ไม่ว่าจะดูสมเหตุสมผลแค่ไหน

**สาม — กับดักที่หมุนปุ่มลงแล้วแย่ลง**

> **หมุนสัดส่วนแกนตั้งของ Recoil Control ลงเพื่อแก้อาการดึงเกิน แล้วมันแย่ลง**

เครดิตของมือสะสมแบบ **ไม่ถูกสเกล** ขณะที่การลงบัญชีที่ขอบนัดซึ่งบริโภคเครดิตนั้น
**ถูกคูณด้วยสัดส่วนแกนตั้ง** ที่สัดส่วน = 0 — ซึ่งยังนับเป็นความต้องการใช้งานอยู่ เพราะ
เงื่อนไขคือ *เปิด และ (แกนตั้ง > 0 หรือ แกนนอน > 0)* — **ไม่มีอะไรบริโภคเครดิตเลย**
ค่าจึงค้างอยู่ที่พื้นตลอดทั้งชุดยิง

**Echo ต้องออกแบบให้การสะสมและการบริโภคเครดิตถูกสเกลด้วยตัวเดียวกัน** หรือไม่ก็ต้องมี
test ที่ตรึงพฤติกรรมที่สัดส่วน = 0 ไว้อย่างชัดเจน

### กฎที่พาโปรดักต์เดิมมาถึงตรงนี้

- **หลักฐานมาก่อนการแก้** อย่าแก้ code บนสมมติฐาน สาเหตุที่อธิบายขนาดของสิ่งที่วัดได้
  ไม่ได้คือสาเหตุที่ผิด — เอาต้นทุนที่วัดได้หารด้วยหน่วยที่ขับมัน แล้วตรวจเลข
- **ตรวจค่าจริงของ field ก่อนนับมัน** เงื่อนไขที่ไม่ตรงกับอะไรเลยแยกไม่ออกจากศูนย์จริง
- **แถวข้อมูลมีอยู่เพราะมีอะไรเลือกบันทึกมัน** ก่อนเทียบ capture สองอัน ตรวจว่าเงื่อนไข
  การบันทึกเปลี่ยนหรือไม่
- **รายงานการทำนายที่ผิดตรงๆ** การวัดที่หักล้างแผนคือผลลัพธ์ ไม่ใช่ความถอยหลัง
- **ไม่ทิ้งปัญหาที่รู้แล้วไว้โดยไม่บันทึก** ของเดิมไม่มีเครื่องหมายงานค้างเลยสักตัวทั่วทั้ง
  source Echo รักษามาตรฐานนั้น

### เรื่องขนาด

ของเดิมราว 128,000 บรรทัดที่ไม่ใช่ test ใน 670 ไฟล์ บัญชีสิ่งที่ยกมาตัดสัดส่วนใหญ่
ออกไป และโมดูลที่เป็นข้อบกพร่องจริงอยู่ราว 5,000 บรรทัด **งานส่วนใหญ่คือการถ่ายทอด
และการตรวจสอบ ไม่ใช่การออกแบบ** — การตัดสินใจเชิงออกแบบคือที่บันทึกไว้ข้างบน
และมันถูกตัดสินไปแล้ว
